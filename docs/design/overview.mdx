# Overview

This document describes how Yapparatus works, for the people and agents who change its code. To write a document with Yapparatus, read the authoring guide.

## What Yapparatus does

Yapparatus lets a person and their coding agent write and revise a technical document together. The agent writes the pages. The person, called the reader, reads them in the browser, selects something on a page, and comments on it in a message to the agent. A message can be a question, a correction, or a request to change the page. The agent revises the page, replies in the chat beside the page, or both. The agent is the reader's own coding agent, running in a terminal.

Three properties make this work. First, the agent can write a rich document with little effort. It writes short MDX pages, and Yapparatus lays them out and draws their diagrams, charts, and code excerpts. Yapparatus reports every error with its file and line, so the agent fixes its own pages. Second, everything on a page has an address: a sentence, a table row, a shape in a diagram, or a few lines of a source file. The reader can point at exactly what a comment is about. Third, the page is live. An edit by the agent appears while the reader reads.

People use Yapparatus for:

- Understanding a codebase. The agent explains unfamiliar code with diagrams and excerpts of the real files, and the reader comments where something is unclear.
- Design documents. The reader directs, and the agent writes and redraws.
- Reviewing a plan or a change. The agent explains what it intends to do or what it did, and the reader marks what to change.
- Reports, such as benchmarks, incident analyses, and comparisons, with charts drawn from the data files that a tool produced.
- Teaching material about protocols, data layouts, and algorithms, with diagrams that the reader steps through.

A finished document can be built as a static website or as one HTML file, without the chat.

The [web app](web-app) is a React app that shows the pages and the chat panel. The [server](server) is a Vite dev server that the `yap` command starts for one [document directory](documents). Its [page compiler](page-compiler) compiles the pages with their [diagrams](diagram-compiler) and [charts](charts), and its [REST API](rest-api) keeps the chat and the [diagnostics](diagnostics). The agent calls the [agent library](agent-library) from shell commands, and everything it reads is text that the server writes.

## Runtimes

Each part of Yapparatus has one runtime. Pure code uses neither the DOM nor Node, so the server, the agent library, and the web app can all import it. Node code runs in the server's process or the agent's process. Browser code runs in the web app. <Ref to="overview-parts" /> lists the parts, their runtimes, and the parts that each may import.

<Table id="overview-parts" caption="The parts of Yapparatus, their runtimes, and what each may import.">

| Part | Runtime | May import | Holds |
|---|---|---|---|
| Document | Pure | Nothing | [Pages, addresses](documents), references, and diagnostics |
| Protocol | Pure | Document | The types of the [REST API](rest-api), and the logger |
| Diagram | Pure | Document | The [diagram compiler](diagram-compiler) |
| Chart | Pure | Document | The [chart](charts) data and specification checks |
| Compiler | Node | The pure parts | The [page compiler](page-compiler) and its [stages](page-compiler#pipeline), reading [external files](documents#external-files), and the checks of `document.json` and of links |
| Server | Node | Compiler and the pure parts | The [server](server) |
| Agent | Node | Protocol and document | The [agent library](agent-library) |
| Vite | Node | Compiler, server, and the pure parts | The `yapparatus()` plugin, which combines the compiler and the server, and the [`yap` command](server#starting) |
| Web | Browser | The pure parts | The [web app](web-app) |

</Table>

The type checker enforces the rule. Each part is a TypeScript project with the library and types of its runtime and a reference to each part it may import. The pure parts have neither the DOM library nor Node's types, the Node parts have Node's types, and the web app has the DOM library and Vite's client types. An import from a part that a project does not reference is an error, and so is a name from another runtime, such as `document` in the diagram compiler.

Two pure parts need more than the standard library. The chart part has the DOM library, because the types of Observable Plot, which the chart specification uses, name DOM types. The logger runs in both runtimes, so its declarations give it the console methods that both runtimes have and the level that Vite's `define` gives the browser. The web app declares the [document module](page-compiler#the-document-module), the other virtual modules, and the single-file build's constant.

The `yap` command and the `yapparatus/vite` and `yapparatus/agent` entries are compiled to JavaScript before they are published, so the compiled package holds only Node and pure code. The web app is published as source, and the Vite of the project that uses it compiles it.
