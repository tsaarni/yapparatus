# Overview

This document describes the design and implementation of Yapparatus. The [authoring guide](https://github.com/tsaarni/yapparatus/tree/main/starter/docs) describes how to write documents.

## Purpose

Yapparatus is a tool in which a coding agent writes a technical document and the user comments on it. The user reads the pages in the browser, selects something on a page, such as a sentence, a shape in a diagram, or lines of code, and comments on it in the chat beside the page. A comment can be a question, a correction, or a request to change the page. The agent revises the page, replies in the chat, or both. The agent is the user's own coding agent, running in a terminal.

Three properties of the design support this. First, the agent can write pages with diagrams, charts, and code excerpts, and check the result without a browser:

- The agent describes a diagram as rows, columns, and placements in a short JavaScript program, and the [diagram compiler](diagram-compiler) computes every size and position. A language model states an arrangement well and computes coordinates poorly.
- The diagram compiler reports overlapping shapes, edges that cross shapes, and text that does not fit. The agent can also save a [picture](diagram-compiler#pictures) of a diagram and look at it.
- The agent writes chart data as a table or a CSV file, and draws it with Observable Plot, which agents already know. The page compiler checks the data.
- The agent shows code from the source files without copying it into the page, so the page stays up to date when the code changes.
- Figures, tables, and listings are numbered automatically, and every color comes from the theme. The agent writes no numbers and no colors.
- Every problem, such as a broken link, is reported with its file and line, so the agent fixes its own pages.

Second, everything on a page has an address: a sentence, a table row, a shape in a diagram, or a few lines of a source file. The user can point at exactly what a comment is about. Third, the page is live. An edit by the agent appears while the user reads.

The user and the agent can use it for:

- Understanding a codebase. The agent writes an overview of the codebase with diagrams and excerpts of the code, and the user asks about what is unclear.
- Design documents. The user directs, and the agent writes the text and draws the diagrams and charts.
- Reviewing a pull request. The agent explains the change, and the user asks questions about it.
- Troubleshooting. The agent charts measurements from data files, such as latency during an outage.
- Teaching material about protocols, data layouts, and algorithms, with diagrams that the user steps through.

A finished document can be built as a static website or as one HTML file, without the chat.

The [web app](web-app) is a React app that shows the pages and the chat panel. The [server](server) is a Vite dev server that the `yap` command starts for one [document directory](documents). Its [page compiler](page-compiler) compiles the pages with their [diagrams](diagram-compiler) and [charts](charts). Its [REST API](rest-api) serves the chat and the [diagnostics](diagnostics) to the web app and the agent. The agent calls the [agent library](agent-library) from shell commands, and everything it reads is text that the server writes.

## Source directories

The source code is split into directories. Code in each directory runs in Node, in the browser, or in both. Node code runs in the server's process or the agent's process, and browser code runs in the web app. Shared code uses neither Node nor the DOM, so the server, the agent library, and the web app can all import it. <Ref to="overview-directories" /> lists the directories, where their code runs, and what each may import.

<Table id="overview-directories" caption="The source directories, where their code runs, and what each may import.">

| Directory | Runs in | May import | Holds |
|---|---|---|---|
| Document | Both | Nothing | [Pages, addresses](documents), references, and diagnostics |
| Protocol | Both | Document | The types of the [REST API](rest-api), and the logger |
| Diagram | Both | Document | The [diagram compiler](diagram-compiler) |
| Chart | Both | Document | The [chart](charts) data and specification checks |
| Compiler | Node | The shared directories | The [page compiler](page-compiler) and its [stages](page-compiler#pipeline), reading [external files](documents#external-files), and the checks of `document.json` and of links |
| Server | Node | Compiler and the shared directories | The [server](server) |
| Agent | Node | Protocol and document | The [agent library](agent-library) |
| Vite | Node | Compiler, server, and the shared directories | The `yapparatus()` plugin, which combines the compiler and the server, and the [`yap` command](server#starting) |
| Web | Browser | The shared directories | The [web app](web-app) |

</Table>

<Ref to="overview-imports" /> draws the same rule. The web app and the server have only the shared directories in common, and so do the server and the agent library.

The type checker enforces the rule. Each directory is a TypeScript project with the library and types of where its code runs, and a reference to each directory it may import. The shared directories have neither the DOM library nor Node's types, the Node directories have Node's types, and the web app has the DOM library and Vite's client types. An import from a directory that a project does not reference is an error, and so is a name from the wrong environment, such as `document` in the diagram compiler.

Two shared directories need more than the standard library. The chart directory has the DOM library, because the types of Observable Plot, which the chart specification uses, name DOM types. The logger runs in Node and in the browser, so its declarations give it the console methods that both have and the level that Vite's `define` gives the browser. The web app declares the [document module](page-compiler#the-document-module), the other virtual modules, and the single-file build's constant.

The `yap` command and the `yapparatus/vite` and `yapparatus/agent` entries are compiled to JavaScript before they are published, so the compiled package holds only Node and shared code. The web app is published as source, and the Vite of the project that uses it compiles it.
