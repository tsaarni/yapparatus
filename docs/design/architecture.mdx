# Architecture

Yapparatus consists of an app that runs in the browser and a development server. Both use the same project directory. The reader's own agent runs in a terminal alongside them. This page describes how a project is created, what the browser, the server, and the agent each do, how they communicate, and where their code is.

## Creating a document

A new document starts as a copy of the [`starter/`](/-/files/yapparatus/starter/README.md) template:

1. The user copies `starter/` to a new directory and installs its dependencies. The starter is a working document of one page that says it is empty.
2. The user starts the dev server with `pnpm dev content` and opens the address that it prints. The browser shows the empty document.
3. The user chooses **Ask** to open the chat. No agent is connected yet, so the chat offers a **Copy prompt** button.
4. The user starts a coding agent in the project directory and pastes the prompt into it. The prompt tells the agent how to connect to the chat.
5. The user asks in the chat for a document on some topic. The agent writes the pages in `content/`, and the browser shows them as they change. From here on, the [reading loop](overview#purpose) runs.

## Document directories

A project can hold several documents. Each one is a document directory: a directory with its own `document.json` and pages, such as `content/` in the starter or `docs/design/` in this repository. The project's `icons/`, `docs/`, and dependencies are shared.

1. **The server runs one document at a time,** given as a path relative to the project directory: `pnpm dev docs/design`. The `yap` command in [`src/cli.ts`](/-/files/yapparatus/src/cli.ts) takes the path and passes it to the Vite plugin, as `vitepress dev docs` does for VitePress. A Vite script cannot take it, because `vite <path>` reads the path as Vite's root. There is no default document, so the command always names the one it serves.
2. **A project's `vite.config.ts` is loaded when it exists,** so a project can add Vite options and plugins. The command adds `yapparatus()` itself, and the plugin refuses to run twice. The server listens only on `127.0.0.1`, and the command has no option to change that, because the chat server trusts every process that can reach it. See [the library implementation](chat#library-implementation).
3. **Every output mirrors the document's path.** The chat is in `.yapparatus/<directory>/`, the website build in `dist/<directory>/`, and the single file in `dist-single/<directory>/index.html`. A document's chat and builds therefore never mix with another document's.
4. **A document directory cannot contain another one.** The pages are every MDX file under the directory, and the chat state mirrors the path. A document in `docs/` would therefore take the pages of `docs/design/` as its own. The server refuses to start, and names both directories.
5. **The project has one `.yapparatus/server.json`.** The newest server writes it, so the agent library finds whichever document is running, and the snippets do not name a document.

## Communication

The programs do not share memory. They communicate in only two ways: through HTTP messages and through files in the project directory.

**The server API sorts messages by kind.** Each kind of message travels in one direction and has one module that handles it. The types are defined in [`src/protocol.ts`](/-/files/yapparatus/src/protocol.ts):

- **Commands** are `POST` requests, such as a new message from the reader or a reply from the agent.
- **Reports** are `PUT /-/api/diagnostics/{scope}` requests. The browser uses them to send the problems it found, by code: the server adds each code's severity and refuses a code it does not know. See [diagnostics](diagnostics#codes-and-severity).
- **Events** are sent to the browser as a stream from `GET /-/api/events`.
- **Reads** are `GET` requests. A read with a `timeout` parameter waits until there is new data, and `GET /-/api/agent/diagnostics` waits until the checks of recent edits are done. The [agent channel](chat#api) uses such reads.

All text that the agent reads, from prompts to error messages, is written in [`src/server/prompt.ts`](/-/files/yapparatus/src/server/prompt.ts).

### Agent library

[`src/agent.ts`](/-/files/yapparatus/src/agent.ts) is the package's `yapparatus/agent` export. It provides the functions `wait()`, `reply()`, and `check()`. The agent calls them from snippets, which are short TypeScript programs that the agent runs. The library runs in the agent's Node process. It finds the server through `.yapparatus/server.json`, and it prints only the text that the server writes. [The section on waiting](chat#waiting) describes the library's behavior.

### Logging

[`src/logger.ts`](/-/files/yapparatus/src/logger.ts) is the logger for the dev server, the browser, and the agent library. `createLogger("chat")` returns the functions `debug`, `info`, `warn`, and `error`. Each line they write is tagged `[yapparatus:chat]`.

1. **One setting, `YAPPARATUS_LOG`, sets the level everywhere:** `debug`, `info`, `warn` (the default), `error`, or `silent`. Node reads the setting from the environment. The plugin passes the value to the browser through Vite's `define` option, so the browser logs at the same level as its server.
2. **In Node, every level is written to stderr,** because the agent reads the agent library's stdout as its prompt.
3. **The default level shows only what needs attention.** Requests, events, and reply checks are logged at `debug`. Changes to the chat and to diagnostics are logged at `info`. When a snippet fails, the agent reads the snippet's stderr. For this reason, the library logs nothing at the default level.
