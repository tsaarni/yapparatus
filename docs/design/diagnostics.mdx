# Diagnostics

Diagnostics are the errors and warnings in a document. Examples are a page that does not compile, a broken link, a diagram whose boxes overlap, and a page or reply that fails to render. The agent uses diagnostics more than the reader does, because the agent edits the pages and can fix the problems. This page describes where diagnostics come from, how they are identified, and who sees them.

## Where diagnostics come from

1. **The server checks everything that it can find from the source files.** Whenever a file changes, the server compiles every page and checks links, references, and `document.json`. Compiling also checks the Markdown conventions: code block languages, heading depth, alert kinds, file trees, tabs and columns, and figures inside figures. None of these checks need a browser.
2. **Compiling a page compiles its diagrams.** The page compiler runs each `draw`, measures the text with the reader's font files, and checks the layout and the steps. A diagram's diagnostics are therefore compile diagnostics of its page, found on every save, whether or not a browser has the page open. Each one names the figure as its target, the parts, and the figure's lines. See [where a diagram is compiled](diagrams#where-a-diagram-is-compiled).
3. **The browser checks what can be found only when a page runs.** These checks cover chart marks, render errors, runtime errors, and replies that fail to show. A chart is drawn by Observable Plot in the browser at the width of the page, so its checks need a browser. [What the browser reports](#what-the-browser-reports) describes how its diagnostics reach the server.
4. **A reply is checked like a page before it is stored.** Its problems are diagnostics with the codes pages use, such as `BROKEN_LINK`, `COMPILE_FAILED`, or a diagram's `UNKNOWN_PART`, plus `UNKNOWN_COMPONENT` and `REPLY_EMPTY`, which only a reply can have. Errors keep the reply out, and warnings do not. The errors are not stored: they come back to the agent in the refusal. See [replying](chat#replying).
5. **[Direction](directions):** an open tab also renders, off screen, the pages that it does not show, so that one tab checks the charts and render errors of the whole document. Browsers slow down background tabs, so this needs testing first.

### What the browser reports

A page's revision is a hash of its text and of every file it reads: the files of its excerpts and its charts' data. The compiler writes the revision into the page, and the server computes it from the files on disk. A change to any of these files gives the page a new revision.

1. **A diagnostic belongs to the revision of the page that the browser rendered.** The browser sends it with `POST /-/api/diagnostics` and `{ source, revision, diagnostics }`. See [report diagnostics](api#report-diagnostics). A revision never changes, so the diagnostics reported for it stay true.
2. **A report only adds diagnostics.** The browser does not report that a problem is fixed. A fix changes the page, the page gets a new revision, and the diagnostics of the old revision stop counting. The current diagnostics are the server's checks and the diagnostics reported for each page's current revision.
3. **A page reports every revision it renders, even without diagnostics.** That report marks the revision as checked. A chart without diagnostics sends nothing.
4. **A page that no browser has rendered since it changed is unchecked.** Its charts, render errors, and runtime errors are not known for its current revision. Its diagrams are, because the server checks them. The server lists the page with the diagnostics of the revision that a browser rendered last. An empty list therefore means that the checked pages have no problems. The agent can also tell an old error that is not confirmed from one that is gone. The server keeps the diagnostics of the last three revisions of each page.
5. **Runtime errors belong to the revision of the page on screen.** On a file view, they are only logged.
6. **A reply never changes,** so its diagnostics have no revision and count for as long as the reply is in the chat.
7. **Diagnostics from several tabs add up.** A chart's tick labels can overlap at one width and not at another. The warning counts, because some readers see the overlap.
8. **The revision does not cover components.** A change to a component, built in or in the document's own `.tsx` files, updates the page without a new revision. A diagnostic that a component caused therefore stays after the component is fixed, until the page changes or the server restarts.

## Codes and severity

1. **Every code is in one registry, with its severity.** `diagnosticCodes` in `protocol.ts` maps each code to its severity and one line on what it means. `DiagnosticCode` is the union of its codes. A check passes a code, and the registry supplies its severity. One code therefore cannot be an error in one checker and a warning in another.
2. **A code names what is wrong, in the words of the authoring guide.** The registry stores the severity, so a code has no `_ERROR` suffix. Each problem has one code, and every checker uses the same code for the same problem. A duplicate is `DUPLICATE_ID` whether two pages, a heading and a figure, or a step and a part share the id.
3. **The severity follows one rule.** A code is an `error` when the result is not what the author wrote: a reference to nothing, a duplicate, an invalid form, or something that threw. It is a `warning` when the page renders as written but reads badly: overlap, overflow, or too much. The rule guides the choice of severity for each code in the registry. The registry stores each severity as a fixed value.
4. **The server adds the severity to reports.** The browser sends codes without severity. The server refuses a report whose code is not in the registry. It adds each code's severity when it lists diagnostics, in the updates that it sends to the browser, and in the agent's text. A browser that runs old code therefore cannot contradict the registry.
5. **The registry has no classes of codes.** A layered taxonomy would use a fixed list of problem words, classes such as "failure, mistake, flaw", and a severity derived from the class. That would make codes less descriptive and would need exceptions. The registry uses a code for three things: as identity, as a label in the header list and the agent's prompt, and for its severity. Nothing would read a class.

## How diagnostics are identified

**A diagnostic is identified by its code, file, target, and subject.** The subject is what the diagnostic is about, such as a link's target or a diagram's parts. With this identity, a diagnostic whose message is reworded is still the same diagnostic. Two broken links on one page are two separate diagnostics. When a diagnostic has no subject, its message identifies it.

## Who sees diagnostics

1. **The agent checks the document after editing and before replying.** `checkDocument()` reads [`GET /-/api/diagnostics`](api#read-the-diagnostics), which waits until the checks of recent edits are done. The file watcher reports an edit a moment after the file is saved. The read therefore compares the save times of the pages with the start of the last check, and runs the checks again when a page is newer. It returns every diagnostic and the unchecked pages, with text for the agent. The errors it returns count as given to the agent. It claims no agent, so it runs beside an open wait.
2. **The agent learns about later errors without asking.** Some errors, such as a chart that fails, appear only when a browser opens a changed page, after the agent replied. The server remembers which errors it gave the agent, by [their identity](#how-diagnostics-are-identified). An error that has existed for 2 s and that the agent has not been given ends the agent's wait, as a reader message does. The prompt then lists all diagnostics with the new errors marked. See [waiting for messages](chat#waiting-for-messages).
3. **Errors in the document do not hold back a reply.** The server checks only the reply's own MDX, components, and links. The agent checks the document's errors. See [replying](chat#replying).
4. **The agent reads one line per diagnostic, the same everywhere.** A prompt, a diagnostics read, and a refused reply all write `- error CODE file:lines, /page#figure, parts a, b: message`. The server fills in a figure's lines from the page as it is now. The address is the one the agent links in its reply. A reply being checked has no file yet, so its problems name only the line.
5. **Short-lived errors and warnings never end the agent's wait.** An error that disappears within 2 s, such as one caused by a file that was saved half-written, never wakes the agent. Warnings do not end a wait, so the agent spends no turn on them.
6. **The reader sees diagnostics in the page and in a list.** A page that fails shows its error. A diagram or chart shows its diagnostics under the figure. When there are errors or warnings, the header shows how many there are. Each item in the list opens the place it is about. **Ask** attaches that place to the message box. A diagnostic therefore reaches the chat only when the reader asks about it.
