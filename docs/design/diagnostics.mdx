# Diagnostics

A diagnostic is one error or warning in a document, such as a broken link or two boxes that overlap in a diagram. This page follows a diagnostic from the check that finds it, through the server, to the agent and the reader.

## Overview

The server finds problems in the source files, and the web app reports those that appear only when a page runs. Both go into one diagnostic store in the server. <Ref to="diagnostics-flow" /> follows one edit to the error that ends the agent's next wait.

The store is in [`src/server/diagnostics.ts`](/-/files/yapparatus/src/server/diagnostics.ts). The requests that read and report diagnostics are in [the REST API](/rest-api#diagnostics).

## Origins

Every diagnostic records which check found it as its [origin](/-/files/yapparatus/src/protocol.ts#L140-L152).

After every change, the server checks `document.json` and its page list (origin `pages`), compiles every page (origin `compile`), and checks links and references across pages (origin `link`). Compiling a page also checks its [Markdown conventions](/page-compiler#markdown-conventions), its charts' data, and its [diagrams](/diagram-compiler#checks).

The web app checks what exists only when a page runs: [the marks of a chart](/charts#checks-on-the-marks) (origin `chart`), a page that throws while it renders (origin `render`), an error outside rendering (origin `runtime`), and a reply that cannot be shown (origin `reply`). It reports them to the server.

The server also [checks each reply](/server#reply-checks), and returns its errors to the agent without storing them.

**[Direction](directions):** an open tab also renders the pages it does not show, off screen, so one tab checks the whole document. Browsers slow down background tabs, so this needs testing first.

## Codes and severity

Every code is in one registry in `src/protocol.ts`, with its severity and meaning. <Ref to="diagnostics-registry" /> shows its start.

A check passes a code and never a severity, so a code has the same severity everywhere. Each problem has one code: any two things that share an id are `DUPLICATE_ID`.

A code is an `error` when the result is not what the author wrote: a reference to nothing, a duplicate, an invalid form, or something that threw. It is a `warning` when the page renders as written but reads badly: overlap, overflow, or too much of something.

The web app sends codes without a severity, and the server adds it from the registry.

## Identity

A diagnostic is identified by its code, file, target, and subject, as <Ref to="diagnostics-type" /> marks.

The target is a figure id on a page, or a message number in a reply. The subject is what the diagnostic is about, such as a link's target, or else its message. So a diagnostic whose line moves stays the same, and two broken links on one page stay two. The store uses it to drop duplicate reports and to remember which errors the agent has been given.

## Revisions and reports

The web app's findings belong to a [revision](/page-compiler#revisions) of a page: a hash of the page's text and of every file it reads.

The web app sends one report for every revision it renders: an empty list when the page renders, `RENDER_FAILED` when it throws, and what its charts found.

A report only adds diagnostics. A fix changes the revision, and the old revision's findings stop counting. The store's list holds the server's checks, the findings for each page's current revision, and those for replies still in the chat. Reports from several tabs add up, because a chart can overlap at one width only.

A page is unchecked when no web app has rendered its current revision. Its diagrams are known, because the server checks them, and its charts and render errors are not. The store lists it with what the last rendered revision found, so the agent can tell an unconfirmed error from one that is gone.

A change to a component's code does not change a revision, so a finding the component caused stays until the page changes or the server restarts.

## What the agent sees

The agent reads diagnostics in the prompt of a wait, in the result of `checkDocument`, and in the refusal of a reply, one line per diagnostic. <Ref to="diagnostics-line" /> marks the parts of one line.

`new` marks an error the agent has not been given. The agent links the address in its reply. New errors come first, and the unchecked pages follow.

[`checkDocument`](/agent-library#checkdocument) first checks again any file saved after the last check started, because the file watcher reports an edit a moment late. It then waits a few seconds at most, so an open web app can report. The errors it returns count as given.

[`waitForMessage`](/agent-library#waitformessage) returns reader messages and new errors. An error ends a wait when it has lasted 2 s and has not been given. Warnings never end a wait. An error that is fixed and comes back is new again.

## What the reader sees

In dev mode, the web app shows diagnostics under each diagram and chart, in place of a page that throws, and in a menu in the header, which lists them by page. **Comment** in the menu starts a message about the diagnostic. A diagnostic reaches the chat only this way. A build shows none. See [diagnostics display](/web-app#diagnostics-display).

## Design decisions

**Reports are tied to a revision and only add.** A report that replaced earlier findings would need the web app to know when a problem is fixed, and reports from several tabs would overwrite each other. With revisions, a report never has to be taken back.

**An error must last 2 s before it ends the agent's wait.** Otherwise the agent would spend a turn on each error that exists only while a file is half-written or an edit across two files is in progress.
