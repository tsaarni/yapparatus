# Diagnostics

A diagnostic is one error or warning in a document, such as a broken link or two boxes that overlap in a diagram. This page follows a diagnostic from the check that finds it, through the server, to the agent and the user.

## Overview

The server finds problems in the source files, and the web app reports those that appear only when a page runs. Both go into one diagnostic store in the server. <Ref to="diagnostics-flow" /> follows one edit to the error that ends the agent's next wait.

The requests that read and report diagnostics are in [the REST API](/rest-api#diagnostics).

## Origins

Every diagnostic records which check found it as its origin.

After every change, the server checks `document.json` and its page list (origin `pages`), compiles every page (origin `compile`), and checks links and references across pages (origin `link`). Compiling a page also checks its [Markdown conventions](/page-compiler#markdown-conventions), its charts' data and marks, and its [diagrams](/diagram-compiler#checks).

The web app checks what exists only when a page runs: [the drawing of a chart](/charts#checks-on-the-marks) (origin `chart`), a page that throws while it renders (origin `render`), an error outside rendering (origin `runtime`), and a reply that cannot be shown (origin `reply`). It reports them to the server.

The server also [checks each reply](/server#reply-checks), and returns its errors to the agent without storing them.

**[Direction](directions):** in dev mode, the server renders each page with React in Node after it compiles the page, and reports a page that throws as origin `render`. Every page is then checked for render errors with no browser open. See [builds](/page-compiler#builds).

## Codes and severity

Every code is listed once, with its severity and meaning.

A check passes a code and never a severity, so a code has the same severity everywhere. Each problem has one code: any two things that share an id are `DUPLICATE_ID`.

A code is an `error` when the page cannot be shown as written: a reference to nothing, a duplicate, an invalid form, or something that threw. It is a `warning` when the page renders as written but reads badly: overlap, overflow, or too much of something.

The web app sends codes without a severity, and the server adds it from that list.

A message names what is wrong, with the values and ids involved, and says how to fix it.

## Identity

A diagnostic is a `Diagnostic`. It holds its `origin`, `code`, and `message`, and when known the `source` file relative to the project, the `line` in it, a `target`, a `subject`, and the ids of the diagram `elements` involved. A diagnostic is identified by its `code`, `source`, `target`, and `subject`.

The target is a figure id on a page, or a message number in a reply. The subject is what the diagnostic is about, such as a link's target, or else its message. In a diagram, it is the ids of the elements followed by the name of the option, such as `a->c route`, so two problems on one element, or one problem on two elements, stay two. So a diagnostic whose line moves stays the same, and two broken links on one page stay two. The store uses it to drop duplicate reports and to remember which errors the agent has been given.

## Revisions and reports

The web app's findings belong to a [revision](/page-compiler#revisions) of a page.

The web app sends one report for every revision it renders: an empty list when the page renders, `RENDER_FAILED` when it throws, and what its charts found.

A report only adds diagnostics. A fix changes the revision, and the old revision's findings stop counting. The store's list holds the server's checks, the findings for each page's current revision, and those for replies still in the chat. Reports from several browser tabs add up, because a chart can have a problem at one window width and not at another.

A page is unchecked when no web app has rendered its current revision. Its diagrams and chart marks are known, because the server checks them, and its chart drawings and render errors are not. The store lists it with what the last rendered revision found, so the agent can tell an unconfirmed error from one that is gone.

A change to a component's code does not change a revision, so a finding the component caused stays until the page changes or the server restarts.

## What the agent sees

The agent reads diagnostics in the prompt of a wait, in the result of `checkDocument`, and in the refusal of a reply, one line per diagnostic. <Ref to="diagnostics-line" /> marks the parts of one line.

`new` marks an error the agent has not been given. The agent links the address in its reply. New errors come first, and the unchecked pages follow.

[`checkDocument`](/agent-library#checkdocument) first checks again any file saved after the last check started, because the file watcher reports an edit a moment late. Checks run one at a time: an edit during a check runs it again, so a check never answers with files older than the request. Vite cannot load a new page until its file watcher reports the file, which can come after a check that runs right after the page was written. A page that Vite fails to load although it is on disk is compiled again once the watcher reports it, or after 2 s. `checkDocument` then waits until the server has checked the edits, and does not wait for a browser: a browser shows one page, often not the edited one. Pages no browser has rendered since they changed are listed as unchecked, and what a browser finds later ends the agent's next wait. The errors it returns count as given.

[`waitForMessage`](/agent-library#waitformessage) returns reader messages and new errors. An error ends a wait when it has lasted 2 s and has not been given. Warnings never end a wait. An error that is fixed and comes back is new again.

## What the user sees

In dev mode, the web app shows diagnostics under each diagram and chart, in place of a page that throws, and in a menu in the header, which lists them by page. **Comment** in the menu starts a message about the diagnostic. A diagnostic reaches the chat only this way. A build shows none. See [diagnostics display](/web-app#diagnostics-display).

## Design decisions

**Reports are tied to a revision and only add.** A report that replaced earlier findings would need the web app to know when a problem is fixed, and reports from several tabs would overwrite each other. With revisions, a report never has to be taken back.

**The fix is in the message, not in the guide.** Agents read a fix when a diagnostic arrives and fix every diagnostic of a check in one round. A table of every code made the guide too long to read in one go, and a shorter guide is read whole.

**`checkDocument` does not wait for browsers.** The server finds almost every problem itself. An open browser shows one page, often not the edited one, so a fixed wait would mostly wait for nothing, and the unchecked list already says what no browser has confirmed.

**An error must last 2 s before it ends the agent's wait.** Otherwise the agent would spend a turn on each error that exists only while a file is half-written or an edit across two files is in progress.
