# Chat and the agent

The chat is the conversation between the reader and an [agent](/overview#chat). The agent channel is the set of requests that the agent uses to talk to the server. This page describes what the chat contains, how the agent reads and answers it through the agent channel, and how the server tells the reader whether an agent is waiting.

## Principles

1. **Each document has one chat, in time order.** One agent waits at a time, and there are no threads. Each message carries its own context. Parallel threads would leave it unclear which agent answers which message.
2. **The agent answers with replies, page edits, or both.** The reader does not choose which. Sometimes the best answer is an edited page.
3. **Replies use the page components.** A reply is a complete MDX message. The browser shows it once the server accepts it. Replies do not stream, because the browser cannot render incomplete JSX.
4. **Edits appear at once** through hot reload, which updates the open page when its file changes. Version control provides undo, so the chat has no approval step and no undo.
5. **The chat stays when the reader moves to another page.** Closing the panel hides the chat, and the agent stays connected.
6. **The server stores chat state outside the document.** It writes the state to `.yapparatus/<directory>/`. No page directory or build includes it, because it holds the reader's questions and selections.
7. **Every prompt includes the diagnostics.** The agent fixes every diagnostic. The reader can write "Fix the errors" without further explanation. See [diagnostics](diagnostics).
8. **The word *chat* is the only name.** The panel, the API, the types in [`src/protocol.ts`](/-/files/yapparatus/src/protocol.ts), and the file `chat.jsonl` all use the word *chat*.

## Messages

1. **The chat is an append-only log.** The server stores it in `.yapparatus/<directory>/chat.jsonl`, with one JSON line per message. `<directory>` is the path of the document directory, so each document has its own chat. See [document directories](architecture#document-directories). A reader message contains its text and its context, captured when the reader sends it. An agent message contains four things: the newest reader message that it answers (`inReplyTo`), the path of its MDX module, the time when the agent first read that reader message (`readAt`), and the time when the server accepted the reply. The server cannot see the work that the agent does, so it stores only what was said and when. Appending never rewrites earlier lines. If a crash cuts a line short, the server skips that line when it loads the log.
2. **The server stores points in time and computes durations.** The waiting time is `readAt` minus the time of the question. The working time is the time of the reply minus `readAt`. Two timestamps answer every question about timing, and a stored duration answers only one.
3. **A message's number is its place in the log.** The first message is number 1. A reply refers to the reader message it answers by this number. The agent never sees the numbers, and the browser shows messages in log order without numbers.
4. **A message has no state.** The server does not track whether a question is open, answered, cancelled, or failed. It does not pair a question with its answer, and it does not mark a message as a follow-up to another message. Every message follows the previous one. A lifecycle that the server assigned would be a guess.
5. **The reader can send at any time.** The agent receives all new messages together, so an addition such as "and the diagram too" reaches it at once.
6. **The server computes which messages are unread from the replies.** The agent has replied up to some reader message, and the reader messages after it are unread. The server records only that the agent replied after a message. The reader judges whether the reply answers it.
7. **The chat has no cancel button.** The browser cannot interrupt the agent, so the reader stops the agent in the agent's terminal. A cancel button could only discard the reply. It would suggest that more was undone than was, because the page edits remain.
8. **The author of a reader message is *reader*.** The reader and the agent's user are often the same person, using two channels. The agent answers messages from the terminal in the terminal, and answers messages from the browser with `sendReply()`. The word *user* does not tell the two channels apart.

### Clearing the chat

1. **The chat lasts as long as the agent's conversation memory.** **Clear chat** deletes every message and reply and keeps no archive, so the panel asks for confirmation first. The reader also clears the agent's memory in the agent and connects the agent again. The server cannot see when an agent forgets. A history that the agent no longer has misleads both the reader and the prompts.
2. **Clearing the chat empties the log.** Numbering starts again at 1. The server also forgets which message it gave the agent, so a reply that the agent sends after the chat was cleared has nothing to answer, and the server refuses it.

## How the agent connects

The reader's agent runs in its own session and terminal. It talks to the server by running short TypeScript snippets that call the `yapparatus/agent` library. The server does not host or start agents. <Ref to="agent-loop" /> shows the first round on an empty chat. The agent drives the loop, and the server answers the agent's requests.

### Alternatives considered

- **ACP** (Agent Client Protocol) works with few agents. It starts a fresh session that does not know how the document was written, and the agent that wrote the document answers questions about it best. ACP also leaves permissions and reconnection to the server.
- **Copy and paste** requires a person to move every message between the browser and the agent, and to mark every reply. People skip steps that they repeat.
- **MCP** (Model Context Protocol) cannot notify an agent that the reader wrote a message. It needs configuration for each agent, and the client sets the timeouts for tool calls. Every coding agent can run Node, but not every agent is configured for a given MCP server.
- **A CLI** returns only text. A library returns data that the agent can filter and combine. One snippet can both reply and wait again.

## Waiting for messages

<Listing id="library-calls" caption="The three calls of `yapparatus/agent`.">

```ts
import { checkDocument, sendReply, waitForMessage } from "yapparatus/agent";

await waitForMessage(); // → { messages, diagnostics, prompt }; waits until there is something
await sendReply(); // MDX from stdin; answers the messages that the last wait returned
await checkDocument(); // → { diagnostics, unchecked, prompt }; once recent edits are checked
```

</Listing>

The agent runs a snippet from the project directory with Node's TypeScript support, as <Ref to="snippet" /> shows. The code is passed in the `-e` argument, so stdin stays free for the reply.

<Listing id="snippet" caption="A snippet that replies and then waits for the next message.">

```sh
node --input-type=module-typescript -e 'import { sendReply, waitForMessage } from "yapparatus/agent"; await sendReply(); console.log((await waitForMessage()).prompt);' <<'MDX'
Show on page highlights a target only when it is sure of it.
MDX
```

</Listing>

1. **`waitForMessage()` returns what the agent has to do.** That is the reader messages that no reply has answered yet, and the errors that the agent has not been given. It waits while there is neither. The agent passes no arguments, because the server knows both.
2. **The server remembers what it gave the agent.** It remembers the newest reader message in the last read, which the next reply answers. It also remembers which errors it gave the agent, by their identity; see [how diagnostics are identified](diagnostics#how-diagnostics-are-identified). The server keeps this in memory for one agent, because only one agent waits at a time.
3. **Unanswered messages come back until the agent replies.** If a snippet is killed before it prints, the next `waitForMessage()` returns the same messages. Nothing is lost.
4. **An error wakes the agent once.** An error must stay for 2 s before it wakes the agent, so a file saved half-written, or an edit across two files, does not wake it. A read that returns an error marks it as given. An error that is fixed and comes back is new again. Every prompt still lists all current diagnostics as text.
5. **`waitForMessage()` returns both data and text.** `messages` and `diagnostics` are objects for code that filters or combines them. `prompt` is text that the server writes for the agent to read, and it contains the instructions.
6. **`waitForMessage()` waits until there is something,** and the agent sets no timeout. The start prompt, which is the first prompt the agent receives, tells the agent to run it in the background. If the agent cannot run commands in the background, it runs the snippet with the longest shell timeout and runs it again when the shell stops it. Background commands have no shell time limit. Each wake by a timer costs a model turn. When the chat is left open overnight, this can be hundreds of turns.
7. **`waitForMessage()` rejects only on a real failure.** Waiting is normal. It rejects when there is no server or when another agent takes over. An agent treats a failing command as something to fix.
8. **Every prompt ends with the exact next snippet.** After messages, the snippet replies and waits in one run. After new errors, the prompt says to fix them and check the document again. The prompt then says to reply if there is a reader to tell, and to wait if there is none. The snippets have no arguments, so the loop keeps working after the agent compacts its conversation memory.
9. **The newest agent takes over.** Each `waitForMessage()` call is one agent, named by a random id that its reads send in the `Yapparatus-Agent` header. When a new agent starts waiting while another one waits, the new one takes over, and the older one rejects with "Another agent took over the chat. Stop waiting." Without this rule, a background snippet left over from an old session could block the session that the person just started.
10. **The start prompt holds the instructions for the whole session.** It says how to run the snippet, where the authoring guide is, and what a reply may use. Later prompts hold only the messages, the diagnostics, and the next snippet. A long session therefore does not spend tokens on the instructions with every message. A new agent session uses the same start prompt, and its first wait returns the messages that are still unanswered.

## Replying

1. **`sendReply()` answers the reader messages that the last wait returned.** A message that arrives while the agent writes its reply stays unanswered. Several replies to the same message are allowed, for example when the agent asks the reader a question, or tells the reader what it fixed after new errors.
2. **The reply is MDX on stdin.** The library sends it as the `mdx` of a JSON message. The agent passes it inline with a quoted heredoc (`<<'MDX'`, so that the shell expands nothing) or from a file with `< reply.mdx`. Empty stdin or a terminal on stdin is an error, so `sendReply()` never waits for input. MDX contains many backticks, and in a template literal `${` would silently become code. Stdin needs no escaping.
3. **Snippets that the server writes put their code in `-e '…'` and use only double quotes,** because a single quote would end the shell argument.
4. **The server checks a reply before accepting it.** It checks that the MDX compiles, that the components exist, and that the links resolve, with the same codes as pages. If a check fails, `sendReply()` rejects with one line per problem, such as `- error BROKEN_LINK line 7: …`, and the agent fixes the reply and sends it again. The browser reports errors that appear only when the reply is rendered, and these errors end the agent's next wait.
5. **The agent checks the document before it replies.** The server does not hold a reply back for errors in the document. The prompt tells the agent to run `checkDocument()` after editing and to fix what it lists, so the reader does not read "done" on a broken page. Errors that only a browser finds later, when the reader opens a changed page, end the agent's next wait.
6. **A refusal carries data as well as text.** The server answers `422` with `{ error, diagnostics }`: `error` is the text for the agent, and `diagnostics` are the problems in the reply. `sendReply()` rejects with a `YapparatusError` whose message is the text and whose `diagnostics` are the data, as `waitForMessage()` returns `prompt` beside `diagnostics`.
7. **A reply with nothing to answer is refused.** That happens when no wait has returned a reader message, or when the reader cleared the chat after the last wait.
8. **The agent replies even when the answer is a page edit,** so that the reader knows what changed. The reply says in a sentence what changed on each page and links to the change. The reader follows the link, and opening the page renders it, which checks its diagrams and charts. The agent needs no browser of its own.

## Checking the document

<Listing id="check-snippet" caption="A snippet that prints the document's diagnostics once recent edits are checked.">

```sh
node --input-type=module-typescript -e 'import { checkDocument } from "yapparatus/agent"; console.log((await checkDocument()).prompt);'
```

</Listing>

1. **`checkDocument()` returns every diagnostic after the agent's edits.** It does not read the chat. Without this call, an agent learns whether an edit broke something only by trying to reply or by waiting for the reader. `GET /-/api/diagnostics` answers after up to 8 s, once the server's checks have run and an open browser has had time to report. It resolves with every diagnostic, the pages that no browser has checked since they changed (with what was found before), and the text to read. Only a browser checks diagrams and charts, and most agents have no browser. The text lists the unchecked pages, as a wait's prompt does, for the agent to link in its reply.
2. **The errors that `checkDocument()` returns count as given.** The next wait does not return them again. The call claims no agent, so it can run while a wait is open.
3. **Every prompt that asks for a reply shows the `checkDocument()` snippet,** to run after editing and before replying, and so do the start prompt and a prompt about new errors.

## The prompt

<Ref to="prompt-example" /> shows a prompt with two reader messages.

<Listing id="prompt-example" caption="A prompt as the agent reads it.">

```text
Reader, 14:02:
--- reader ---
Why does Show on page refuse instead of guessing?
--- end reader ---
Context, at the lines the reader saw. If the file changed since, find each by its address and words:
- text, docs/design/reader-app.mdx:92, /reader-app#show-on-page: “Show on page highlights the target only when it finds exactly one match.”

Reader, 14:03:
--- reader ---
And make the diagram show it too.
--- end reader ---
Context, at the lines the reader saw. If the file changed since, find each by its address and words:
- diagram part, docs/design/reader-app.mdx:58-89, /reader-app#show-on-page-flow--say-gone

Diagnostics: none

Edit pages (/home/me/yapparatus/starter/docs/guide.md) or not, and reply. If you edited pages, check the document first and fix what it lists:

node --input-type=module-typescript -e 'import { checkDocument } from "yapparatus/agent"; console.log((await checkDocument()).prompt);'

Then reply and wait:

node --input-type=module-typescript -e 'import { sendReply, waitForMessage } from "yapparatus/agent"; await sendReply(); console.log((await waitForMessage()).prompt);' <<'MDX'
<your reply>
MDX
```

</Listing>

1. **Reader text is fenced** between `--- reader ---` and `--- end reader ---` lines, and the server's instructions follow in a fixed footer. The agent can therefore tell the reader's words from the instructions of the protocol.
2. **Each context item is one line:** kind, file and the lines the reader saw, address, and the selected words or the open step. The line has no generated numbers and no copy of the source. A reference to lines that the agent can open is more useful than a copy of text that the agent can already read. See [what context is](addresses-and-context#what-context-is).
3. **The prompt tells the agent to find each item by its address and words** when the file changed since the reader attached it. The server sends the lines as the reader saw them, because the agent reads the file before it edits.
4. **Reader messages are labelled with their time.** The reader never sees numbers, so a reply that said "as in #8" would point at nothing.
5. **The start prompt lists the external directories** with their paths relative to the project directory, such as `contour: ../../contour`. The agent uses these paths to read the files itself and to write file addresses in replies.
6. **The snippet replies and waits in one run.** If `sendReply()` rejects, `waitForMessage()` does not run, and the output is the error. Each round is one command, so the agent has one fewer step to forget.

## The agent's state

The server sees an agent only while one of the agent's requests is open. That request is either a read of the chat with the `Yapparatus-Agent` header, which `waitForMessage()` repeats, or a reply. Between requests the server cannot see the agent, so it cannot tell an agent that is writing an answer from an agent that has stopped. The server computes the agent's state from its requests. <Ref to="agent-state" /> shows the three states.

  <Step focus="stop give-up away">A read that closes unanswered, or a long time without requests, makes the agent Away.</Step>
</Diagram>

1. **Waiting means connected.** The agent is waiting while one of its reads is open. It also counts as waiting for 10 s after an empty read, and for 10 s after a reply. An empty read returns no messages and no errors. These 10 s cover the gap between two reads of the same wait, and the gap between a reply and the wait that follows it in the same snippet.
2. **A read that returns messages or errors ends waiting at once.** The agent now works and opens no read until it replies. If the server still counted the agent as waiting, the reader would be told that an agent is connected when none is.
3. **A read that closes before its answer means that the agent stopped.** The agent's process ended, so the agent becomes away at once.
4. **Working means that the agent has unanswered messages and no open read.** This state lasts at most 10 minutes after the agent last received messages. During this time the agent is probably writing the answer. After 10 minutes, or when the reader clears the chat, the agent is away.
5. **Away covers every other case.** Only in this state does the reader see instructions for connecting an agent.
6. **The browser shows the state that the server computes.** When the agent is waiting, the header shows a green dot and "Agent connected". When the agent is working, the dot is grey and the header says "Agent working, not connected". The chat also shows typing dots under the message. "Working" is a guess. The 10 minute limit bounds how long a wrong guess is shown. When the agent is away, the dot is grey and the header says "Agent not connected".
7. **State changes are pushed to the browser** as a `yapparatus:chat` update, including when a 10 s or 10 minute period ends. The server sets a timer for the next expiry, so the browser shows that the agent went away without a reload.

## API

The chat is an append-only log of messages, so one resource serves it: `GET /-/api/chat` reads the log, `POST` adds to it, and `DELETE` empties it. [The server API](api#chat) describes the parameters, the bodies, and examples. This section describes why the chat API has its form.

1. **The browser and the agent read the same resource.** The browser reads the whole chat. An agent's read, with the `Yapparatus-Agent` header, returns what the agent has to do. The agent adds `author=reader`, so that its own reply does not end its next wait, and `include=diagnostics`, so that new errors end a wait as a reader message does. The `prompt` in the response is the same read written as text. The diagnostics remain a resource of their own, and a read of the chat may include the related new errors.
2. **A message names its author.** The body's `author` decides which checks apply. [`src/server/chat.ts`](/-/files/yapparatus/src/server/chat.ts) keeps the log, and [`src/server/chat-resource.ts`](/-/files/yapparatus/src/server/chat-resource.ts) serves the reads, takes the messages, and computes the agent's state. Each module reports its changes, and [`src/server/api.ts`](/-/files/yapparatus/src/server/api.ts) decides who is notified of them.
3. **Every response to an agent has a body that the server writes,** including idle responses and errors, because the server writes the next snippet and the instructions for fixing an error.
4. **The agent's id goes in a header.** An agent's reads carry its id in `Yapparatus-Agent`. The header makes the read an agent's read, and it drives [the agent's state](#the-agents-state).
5. **Each `waitForMessage()` call is one agent.** A new id takes over, and the server answers reads with an old id with `409`. The library repeats short reads, so the server needs the id to tell one long wait from a new one.
6. **The server stores the MDX of an accepted reply in a file,** `.yapparatus/<directory>/chat/<id>.mdx` with a random id, because Vite renders MDX by importing it. The message holds the module path, and the browser imports that path. Only the server names the files. A random name means that a reply after the chat was cleared never gets the module of a deleted reply. Vite does not watch `.yapparatus/`. Before it accepts a reply, the server compiles the reply as a temporary file.
7. **A retried reply may duplicate a message.** On localhost, a lost response is rare and a duplicate is harmless, so this risk is accepted.

## Library implementation

1. **The library handles transport, and the server writes the text.** The library passes `prompt` and the error messages from the server unchanged. The library writes only transport errors, such as a missing server or a lost connection. All wording is therefore in one place.
2. **`waitForMessage()` repeats short reads.** It repeats reads of 25 s until there is something. It retries a dropped connection for 30 s before it rejects. There are three reasons. Node's `fetch` gives up after 300 s without response headers. A restart of the dev server drops a waiting request. A stopped server would otherwise leave the agent waiting forever.
3. **The library is the package's `./agent` export,** and agents import it by package name. It is compiled to JavaScript with type declarations in `lib/`, because Node refuses to strip types from files inside `node_modules`.
4. **Uncaught errors print only the server's text,** without Node's stack frames, and the process exits with code 1. Errors that a snippet catches are not affected. The agent needs the instructions for the fix, and a stack trace does not help.
5. **Snippets use only erasable TypeScript.** Erasable TypeScript is TypeScript whose types can be removed without changing the code. Node removes the type annotations and runs the rest. It does not check types, and enums and parameter properties cause errors.
6. **The library finds the server through `.yapparatus/server.json`** in the project directory or a directory above it. The newest dev server writes this file. When a server closes, it removes the file only if the file still belongs to that server. If the connection is refused, the library rejects with instructions for starting the server. A stale file left after a crash therefore gives the agent instructions for starting the server.
7. **The server uses no token.** Any local process can read `.yapparatus/server.json`, and local processes already have access to the workspace. The threats are web pages and DNS rebinding. The server therefore refuses other origins, accepts requests without an `Origin` header (from the library), and checks the `Host` header.

## Open questions

These are also listed with the other unbuilt work on [Directions](directions).

- Whether every supported agent can run commands in the background and be notified when they finish, or whether some agents must restart the wait after their shell stops it.
- Whether agents keep the wait loop running over a long session, or end their turn and stop waiting.
