# Page compiler

The page compiler turns an MDX page into a JavaScript module that the web app can show, and records what the page contains. This page follows a page through its stages, then covers the list of pages, replies, and builds.

## Pipeline

The page compiler turns a page into a module in stages. Each stage reads or changes the page's syntax tree, which holds its headings, paragraphs, and components. <Ref to="compiler-pipeline" /> shows the stages in order. The stages run inside Vite's MDX plugin, and other Vite plugins add the icons, the styles, and React.

Files are read before the outline is recorded, because the page's [revision](#revisions) covers those files. Highlighting runs after the excerpts and the source marks, so it colors every code block and numbers its lines.

The server also compiles pages for its own use: to find diagnostics, to draw pictures, and to list the pages. It does this apart from the pages it sends to the browser, so the browser's first page load does not wait for it. A page is compiled again when its file changes.

A stage that finds a problem adds an issue for the file. After each compile, the server turns the issues into diagnostics at the page's lines, as [origins](diagnostics#origins) describes. A stage that cannot continue throws, and the compile fails with `COMPILE_FAILED`. <Ref to="compiler-sample" /> shows a page and its module.

## The document module

The web app reads the list of pages from one module, which the compiler writes from `document.json` and the page files. <Ref to="compiler-document-module" /> shows what it holds.

  d.arrow(exports.member("pages"), entry)

The compiler first checks `document.json` and its page list against the files on disk, and reports errors as `PAGE_LIST`.

The module holds every page's outline, so the contents, figure numbers, and `<Ref>` work before any page's code loads. To get the outlines, the compiler compiles every page. A page that fails to compile gets an empty outline, so the contents still list it.

A page's code loads when the page is first shown. When it changes, the module swaps in the new page module and outline and tells the web app, as [hot updates](web-app#hot-updates) describes.

## Markdown conventions

The conventions stage reads Markdown forms and component children and writes what it finds into props, so each component receives plain data. <Ref to="compiler-conventions" /> lists them.

<Table id="compiler-conventions" caption="What the conventions stage reads, what it makes, and the codes it reports.">

| Written | Becomes | Codes |
|---|---|---|
| A blockquote that starts with `[!NOTE]` or another kind | An alert | `ALERT_TYPE` |
| A Markdown list in `<FileTree>` | The tree's entries | `FILE_TREE_INVALID` |
| `<Panel>`s in `<Tabs>` or `<Columns>` | The labels | `PANEL_CONTENT`, `PANEL_LABEL`, `PANEL_NESTED`, `TOO_MANY_COLUMNS` |
| `<Columns>` in a `Figure` or `Listing` | A wide figure | |
| A numbered figure in a `Figure` | Nothing | `FIGURE_NESTED` |
| A fenced code block | A checked language | `CODE_LANGUAGE` |
| A `####` heading or deeper | Nothing | `HEADING_DEPTH` |

</Table>

Code marks, such as `// [!code ++]`, are removed before highlighting, so they work in any language, including JSON.

## Math

`remark-math` reads TeX between `$$` marks, inline in a sentence or as a block on lines of its own. A single `$` stays text, so a price needs no escaping. The math stage runs first among the HTML stages and turns each formula into MathML with [Temml](https://temml.org/), so the browser draws it natively and the page loads no math code or style sheet. The web app draws math in a [math font the system has](styling#typography-and-scales). MathML takes the text color of the theme and prints as it is. TeX that does not parse is `MATH_INVALID` at its line, and the page shows the TeX as code.

## Icons

For each `<Icon name="prefix:name">`, the icon stage imports that one icon, and a Vite plugin turns the import into an SVG component, so a page bundles only the icons it names. The icons come from the installed icon packages and the SVG files in the project's `assets/` directory, which a page names as `assets:name` for `assets/name.svg`. An edit to a file in `assets/` reaches the open pages that show it, and the logo and favicon. A name that is not a literal string cannot become an import, so the page fails with `COMPILE_FAILED`.

**[Direction](directions):** a page shows an image from `assets/` with Markdown, as in `![The settings dialog](assets:settings-dialog.png)`. The compiler turns the path into an import, so the build bundles the file and the single HTML file inlines it. When `assets/` has both `settings-dialog-light.png` and `settings-dialog-dark.png`, the image follows the theme. An image goes in a `Figure` for its caption and address. Images are for what cannot be drawn, such as screenshots and photos; a diagram or a chart stays a draw program, so the agent can read and change it.

## Diagrams

The diagram stage runs each draw program in a fresh JavaScript context without Node's names or the page's, and hands the result and the steps to the [diagram compiler](diagram-compiler), with its lookups: the font measure and the Lucide icons, which it reads once from the icon package. The stage evaluates the call `draw(d)` inside the context with a time limit of 1 second, so an endless loop does not stop the server. The context keeps out names and mistakes but is not a sandbox against an attack. A program that throws is `DRAW_FAILED` at the page's line, and a program that runs past the time limit is `DRAW_FAILED` too.

The compiled diagram replaces the draw program, so the browser receives only data, and its diagnostics become issues of the page. Compiled diagrams are cached by their source, so an edit elsewhere on the page does not compile them again.

## Charts

The chart stage reads and checks each chart's data, runs `plot` on it to [check the marks](charts#checks-on-the-marks), and draws the chart to check the drawing. It keeps the drawing at the widest width, which the server shows as the chart's [picture](charts#pictures). Data written on the page goes into the page. Data from a file is loaded separately, and an edit to the file compiles the page again. See [charts](charts#data-sources).

## Code and excerpts

Code blocks, excerpts, and the [file view](web-app#file-view) share one highlighting function, which uses the Shiki highlighter with the theme's colors. Its result, `HighlightedCode`, holds the language, each token style once as CSS, and each line as pairs of a style's index and a text. Code from a file also holds the number of its first line in the file, and code on a page holds each line's line in the page. Marked lines are highlighted, added, or removed.

For each `<Excerpt>`, the excerpt stage reads the file named in `from`, by the rules in [external files](documents#external-files), and finds the lines:

1. The first line is the only line that contains the `start` text. No match or several are an `EXCERPT_TEXT` error.
2. With `end`, the last line is the next line that contains the `end` text.
3. Without `end`, the excerpt runs to the end of the block that the first line opens, by indentation.

The stage adds a code block with those lines, numbered as in the file, and the bar above it links to them. A file that cannot be read leaves the excerpt empty and is reported as `BROKEN_LINK`.

## Outline and source marks

The outline stage records the page's outline, `PageOutline`, and exports it from the page module. <Ref to="compiler-outline" /> lists what it holds.

<Table id="compiler-outline" caption="What a page's outline holds.">

| Field | Holds |
|---|---|
| `revision` | The page's [revision](#revisions) |
| `title` | The text of the page's `#` heading |
| `headings` | Each `##` and `###` heading, with its depth, id, and text |
| `numbered` | Each captioned block with an id, in page order, with its kind and caption |
| `anchors` | Every id a link may point at: headings and blocks with an explicit id |
| `links` | Each link and excerpt file, with its line and the section it is in |
| `refs` | Each `<Ref>`, with its target and line |

</Table>

Two headings or numbered items with the same id are `DUPLICATE_ID`. A page must have exactly one `#` heading.

The source marks stage marks every top-level block, list item, and table row with its file and lines. The web app reads these marks to turn a selection into references, as [commenting on the page](web-app#commenting-on-the-page) describes.

## Revisions

A page's revision is a hash of the page's text and of every file it reads for excerpts and charts. The outline stage writes it into the outline. The diagnostic store computes it again from the files on disk, as [revisions and reports](diagnostics#revisions-and-reports) describes.

## Replies

The server compiles each reply from the agent with the same page compiler before it accepts it, so a reply's diagrams and excerpts get the checks of a page. [Reply checks](server#reply-checks) describes the rest.

The single file holds everything, so it opens from disk. It uses addresses of the form `#/page#id`, described in [addresses in builds](documents#addresses-in-builds).

A build finds the external files by their addresses in the text of its pages, and stores each one highlighted for the file view.

**[Direction](directions):** the builds are smaller. Today the single file of this document is 2.1 MB, and that of a page with one paragraph is 1.4 MB. Three changes make it about 70% smaller:

- The single file stores its script and styles compressed with gzip, and a small loader unpacks them with the browser's `DecompressionStream` and runs them. The script of this document is 1.5 MB as text and 0.55 MB compressed, as base64 inside the HTML.
- A build keeps only the glyphs of the characters that its output holds, in both fonts and with the weight axis. Today the single file holds every subset that Fontsource ships, 0.57 MB, though this document needs only the Latin ones. The website build loads smaller fonts too. A character that the output does not hold, such as one in a chart's tick labels, which the browser draws, shows in a system font.
- A build holds Observable Plot only when a page has a chart. Today the web app imports it on demand, and the single file inlines every import, so a document without charts carries 0.38 MB of Plot.

**[Direction](directions):** the web app runs on [Preact](https://preactjs.com/) through its React compatibility layer, so custom components stay React components. Preact is much smaller than React DOM, which is about half of the web app's main script. On this document, a trial build that pointed React's imports at Preact made the main script 203 KB instead of 408 KB, 66 KB instead of 128 KB compressed, and the single file 1.86 MB instead of 2.1 MB. Every browser test passed on it. The trial showed two rules that the web app now follows, because React hid what broke them:

- Work that must show in the same frame as a change, such as applying the theme or saving the chat's references, runs in a layout effect. After a click, React runs effects before the browser paints, and Preact runs them after.
- A resize observer never watches an element that its own update resizes. CSS lays out the page beside the chat panel, and a chart reads its width from an element with no height. Preact renders right after the observer's callback, and the browser then reports a resize loop, which dev mode counts as a runtime error.

Preact runs in dev mode and in builds alike, so the browser tests cover what readers get. The cost is React's developer tools and Fast Refresh, and React libraries that the compatibility layer does not support.

**[Direction](directions):** the website build writes the content of each page into the HTML file of its address. Today that file holds only the web app's script, so a reader without JavaScript, a search engine, or an agent that fetches the page sees no text. The build would render the web app with React in Node, once for each address, and the browser would then hydrate the HTML: the web app attaches to the markup it finds and does not draw the page again. Text, tables, code, math, and diagrams are in the HTML, because the page compiler already turns math and diagrams into markup and drawing data. Charts, diagram steps, and tabs work after hydration, and charts would be in the HTML too, drawn as the page compiler [draws them to check them](charts#drawing). The HTML must match the browser's first render, so the web app reads the window width, the theme setting, and stored settings only after hydration. In dev mode, the server renders each page in the same way after it compiles the page, and reports a page that throws as a [render error](diagnostics#origins), so render errors are found on every page with no browser open. The single-file build and the web app in dev mode render in the browser as now. A browser test opens a built page with JavaScript turned off and finds the page's text.

## Design decisions

**Diagrams are compiled with the page.** Compiling in the server finds a diagram's problems on every save without a browser, lets the server refuse a reply with a broken diagram, and keeps the diagram compiler out of the user's download. The cost is that a draw program cannot use the page's imports.

**Excerpts find their lines by text.** Line numbers show the wrong code after lines are added above, and marker comments, as in [mdBook](https://rust-lang.github.io/mdBook/format/mdbook.html#including-portions-of-a-file), change the file. Quoted text, as in the `start-after` option of [Sphinx](https://www.sphinx-doc.org/en/master/usage/restructuredtext/directives.html#directive-literalinclude), fails with an error at the page's line when the file changes.
