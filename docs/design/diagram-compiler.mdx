# Diagram compiler

This page describes how the diagram compiler turns a draw program into a compiled diagram, and how the server draws a picture from it. How the web app shows a compiled diagram is on [the components page](components#diagram).

## Overview

The page compiler finds each `<Diagram>` on a page and [hands its draw program to the diagram compiler](page-compiler#diagrams), together with the ids and focus lists of its steps. The diagram compiler runs in the server. It records what the draw program creates, measures the text, sizes and places every element, routes the edges, checks the result, and returns a compiled diagram: plain data with every coordinate in it. <Ref to="dc-stages" /> shows the stages.

The compiler measures, sizes, and places on demand: it computes a value the first time a later stage asks for it, and keeps it. The order in <Ref to="dc-stages" /> is the order in which results become final.

A stage reports each problem it finds and continues with a usable value, so one compile reports all problems at once. A call in the draw program does the same: it reports a value it cannot use and continues with a stand-in. Only the element limit, the time limit, an exception that the draw program throws, a placement cycle, and an exception in the compiler stop the compile, and the result then has no geometry. A diagram with any error is marked as failed, and the server draws no picture of it.

## The scene

The draw program records elements and arrangements in a scene, which the compiler then lays out. The scene and the object `d` that the draw program receives are two separate things:

- The scene holds the elements, the position owner of each element, the size groups, the groups that steps focus, the categories, the owner and suffix of each element named after another, and the problems the calls report. It has one function for adding each kind of element: a node, an edge, a grid, an enclosure, and a frame. That function applies the element limit, registers the element's category, and connects the element to the scene's report, so that the element can report a problem such as a missing member.
- `d` has only the calls that the diagram reference documents, and each call adds elements through the scene's functions. The draw program cannot reach the scene or change its lists.

A sequence and a tree add their elements through the same functions, with what an author cannot set: a passive element, such as a lifeline, an element that follows an edge, such as an activation bar, and an id derived from another element. Their elements therefore count against the limit and register their categories as the author's elements do.

A call reports a problem with the elements it is about and a message that is written later. The ids of those elements are not final while the draw program runs, so the compiler writes every message and the diagnostic's ids after the id check, from the final ids. A box with `replicas: 9` that settles as `a-2` is reported as `a-2`.

Each call has a signature: its arguments in order, and the options it takes, each with the values it takes. A value is one of a list, a number in a range, text, `true` or `false`, a point, an element of given kinds, a function, a list of values, a list of fixed length such as `[x, y]`, an object of options with their own values, or any one of several values. The signatures are the one list of what each call takes, and the diagram reference names the same options, which a test compares in both directions. The option types of the library are checked against the signatures when the library is compiled, so the two cannot drift apart. The methods of elements and points, such as `port()`, `member()`, and `offset()`, have signatures too.

One check runs every call against its signature before the call records anything. It turns each disagreement into a diagnostic and gives the value to use in its place, so no call throws for what it is given:

- `UNKNOWN_OPTION`: the call does not take the option. The message lists the options the call takes, the nearest first when the name is a few edits away, and the option is ignored.
- `INVALID_ARGUMENT`: the value is not one the argument or the option takes. The message names the call, the value, and the values it takes. The option's default is used. An argument has a stand-in, such as empty text for a label or an empty list for a list, or the call leaves out what it cannot make, such as an edge with an end that is not an element or a point. An item of a list that is not one of the list's values is left out, and an empty cell stands in for a grid's cell.
- A call with several forms takes exactly one form key and only the options of that form. `place()` takes one of `below`, `above`, `leftOf`, `rightOf`, and `at`; the first four take `gap` and `align`, and `at` takes `anchor`. A mark takes one of `text` and `lines`, and a sequence message at most one of `reply` and `async`. No form key, a second one, and an option of another form are `INVALID_ARGUMENT`. A `place()` without a form, or without its options, is ignored.
- An option that the call takes but that has no effect in its form is `INVALID_ARGUMENT` and is ignored: `labelSide` on a start or end without a label, `titleCorner` on an enclosure without a title, `levelGap` in the `indent` layout of a tree, and `reply` or `async` on a message from a participant to itself.
- A route that the edge cannot take is `INVALID_ARGUMENT`, and the edge's default route stands in: a route other than `loop` on an edge from an element to itself, and a `loop` route on any other edge.

The diagnostic's subject is the path of the argument or option, such as `role`, `label.side`, or `messages[2].label`, so two problems on one element are two diagnostics.

**[Direction](directions):** a call that does not exist, such as `d.cilinder(…)`, is `DRAW_FAILED`, and the compiler writes a message that names the nearest call, as it does for `UNKNOWN_OPTION`.

A frame is an element, and the signatures take it wherever they take an enclosure: as a point, an end of an edge, a cell of a grid, a row, or a column, a member of an enclosure, and the element that `place()` positions or places next to. A size group, a tree, and a sequence take only shapes. A frame or an enclosure in a grid, a row, a column, or `place()` passes the signature, and the scene reports it as `NOT_PLACEABLE`.

A call that creates an element returns an object that stands for it, and the program passes it to later calls, such as a row or an edge. <Ref to="dc-scene" /> shows the scene of the running example.

A scene holds at most 2,000 elements, counting nodes with their cells and marks, edges, frames, enclosures, and grids, which include rows and columns. The checks compare elements in pairs, so a larger scene would take minutes to check. The call that would create one more element throws, which is `DRAW_FAILED`.

An element in the scene has no coordinates. A point on it, such as `api.bottom`, or a point computed from others, such as `api.bottom.offset(0, 20)`, is a description that the layout evaluates once the positions it names are known. The order of the statements therefore does not matter.

Each element gets its position from exactly one source: the grid it is in, or the `place()` call that places it. A second source is `CONFLICTING_PLACEMENT`, and the first one stays in force. An enclosure takes its bounds from its members, a frame from its two corners, and a cell or a mark from its parent, so a grid or a `place()` that positions one is `NOT_PLACEABLE`: the grid leaves that cell empty, and the placement is ignored. An element may be placed next to an enclosure or a frame, because that uses the rectangle and owns nothing. Before layout, the compiler looks for elements with no source. The first one goes to the origin, and every other one is reported as `UNPLACED`. In the running example, only the row has no source, so it is at the origin.

A grid holds rows of cells, and each cell is an element or empty. A row is a grid of one row, and a column is a grid of one column, so one layout rule places all three. Grids can be placed like any element, so they nest.

**[Direction](directions):** the diagram reference shows swimlanes as a pattern: a grid with a title on each row. A call for swimlanes is added to `d` only when the pattern is not enough.

## Ids

Every element has an id. The page uses it as the element's address, `/page#figure--element`, and steps, diagnostics, and references refer to elements by it. An element may have an explicit `id`. Without one, the compiler derives an id, as <Ref to="dc-ids" /> lists. The variable that holds an element plays no part. <Ref to="dc-id-example" /> shows each case with its address, for a diagram `request-path` on the page `architecture.mdx`.

  for (const name of ["Worker A", "Worker B"]) d.box(name)

  //   /architecture#request-path--http-api->store

A slug keeps lowercase letters, digits, and underscores, turns every other run of characters into one hyphen, and drops hyphens at either end, so `"Auth service"` is `auth-service`, `"user_id"` is `user_id`, and text with none of these characters is `node`. An author who writes an identifier, such as a column name, reaches its member by that name.

Each call of the author's counts among the calls of its kind, whether or not the element has text or an `id`. A sequence and a tree make their rows, columns, and frames without counting, so they never change the numbers of the author's elements. An element that a sequence or a tree makes is named after its owner: the scene records the owner and the suffix, and the id check joins them once the owner's id is final.

The id check makes the ids final before layout. A repeated explicit id is `DUPLICATE_ID`, and a repeated derived id gets `-2`, `-3`, in the order of creation. Shapes, containers, and frames are settled first. Elements named after an owner are settled after it, so a branch over the root `team-2` is `team-2-tree`. Cells, marks, and edges are settled last, because their ids are built from the final ids of their parents and ends. A lifeline is an edge named after its participant, and it is settled with the edges.

A derived id changes when its label changes. The link check verifies only the figure part of an address, so the [diagram reference](https://github.com/tsaarni/yapparatus/blob/main/starter/docs/diagrams.md#ids) asks for an explicit id on any element that something outside points at.

## Text measurement

Text measurement splits each label into lines at its line breaks, and wraps each line at word boundaries where it is wider than the wrapping width. The text of boxes, cylinders, queues, documents, inputs and outputs, decisions, actors, and icon shapes wraps at 220 units, and notes, free text, and the labels of start and end dots wrap at 320. A sublabel wraps as its node's label does. A fixed `width` sets the wrapping width to the width less the padding. A box's icon and the gap after it take 26 units of the wrapping width, fixed or not. Text in the monospace font and record titles wrap only at a fixed `width`, and record cells and edge labels never wrap. Every line in the compiled diagram carries its font size and weight, and the web app and the picture draw it with exactly those values.

Wrapped lines are balanced. The compiler first fills each line with as many words as fit, which gives a number of lines. It then wraps the text again at the narrowest width, to about one unit, that gives the same number of lines. A two-line label then has two lines of similar length. Each paragraph between line breaks is balanced on its own, also at a fixed `width`. A shape is as wide as its widest line needs, so a box with a long label is at most 220 units plus padding wide. A word wider than the wrapping width stays whole and widens the shape. Only at a fixed `width` is it reported as `TEXT_OVERFLOW`.

The compiler receives the font measure and the icon set together, as its lookups, because it is pure and reads no files. The page compiler supplies the font measure described below and the Lucide set from its icon package, and tests supply fixed ones. The icon set gives the markup of a known name and lists every name. A name is known when it is an icon of the package or an alias of one; a hidden icon, or one that is not on the 24 unit grid, is not. The compiler looks up each icon before it measures text, and a name the set does not have is `UNKNOWN_ICON`, with up to five nearest names: names that contain it, then names a few edits away. The node is then measured and drawn without an icon.

The widths come from the font measure, which reads the font files and `@font-face` rules that the web app loads. For each character, it picks the face that a browser picks, and it shapes the text with fontkit. A browser test checks that its widths are within 0.5 pixels of the browser's own. Chromium on Linux rounds each glyph's advance to a whole pixel when the font is hinted, so there a line can differ by up to half a pixel per character; box padding absorbs this for labels of normal length. The test turns font hinting off, so the browser positions glyphs exactly. A character that no face has gets a width of one em and is reported as `FONT_FALLBACK`, because a browser draws it in a system font of unknown width.

## Layout

The layout answers three questions about any element: its size, its position, and its rectangle, which combines the two. Sizes are computed from the inside out, and positions from the outside in.

### Sizes

A shape's size is its measured content plus padding on each side, and at least a minimum size. A box's content is its icon, when it has one, then a gap, then its text: the icon is 18 units square and the gap 8 units, and the content is at least as tall as the icon. The icon and the text block are centered together in the box, and the icon is centered on the height of the whole text block, label and sublabel. An icon shape is laid out as an actor is: the icon, 30 units square, above its label, 6 units apart, at least 36 units wide, with edges attached to its bounds. A fixed `width` or `height` replaces it. Shapes in a size group, such as `equalSize`, take the largest size in the group, fixed sizes included. A member without a fixed width wraps its text at its shape's wrapping width before the group's size is taken. A member with a fixed size on an axis of the group keeps it, and its text wraps at that width. When that size is smaller than the group's, the group is not equal, and the compiler reports `FIXED_SIZE_IN_GROUP`. A grid's columns are as wide as their widest cells, and its rows as tall as their tallest cells. The grid is as wide as its columns and the gaps between them, and as tall as its rows and the gaps between them. A row of a grid may be shorter than the others, and an empty cell adds nothing to its tracks. An enclosure surrounds its members with padding and a band for its title. A frame lies between its two corners, and a frame with members grows to cover them, as [sequences](#sequences) describe. Some outlines take room beyond the padding, on one axis, and move the text away from it. A cylinder adds its two caps to its height and a queue, a cylinder on its side, to its width. A cap's depth grows with the size across it, from 6 to 12 units. An input or output adds the 14 units of its parallelogram's slant to its width. A document adds the 5 units that its wave rises above its bottom line to its height. The wave crosses the bottom line at its middle, so the middle of the bottom side is on the outline, and its left half dips 5 units below the bounds.

A box or a document with `replicas` is a stack of 2 to 4 of them: the shape in front, and each one behind it 5 units up and to the right of the one before. The stack's size is the front shape's size, with its minimum and its fixed `width` and `height`, plus 5 units on each axis for each shape behind. Rows, gaps, size groups, grids, enclosures, and the overlap checks then use the whole stack with no rule of their own. The text centers on the front shape. Any other number of replicas is `INVALID_ARGUMENT`, which the draw program records, and the shape is drawn alone.

In the running example, "Client" measures 38.0 by 18.6. With the padding, the box would be 70 by 40.6, so the minimum size of 104 by 46 applies. The cylinder adds 7.3 units of cap above and below its text and is 55.2 units tall.

  d.row([dbSize, db, apiRect], { gap: 48, id: "level-1" })

  d.place(d.row([row, offsets], { gap: 48, id: "level-3" }), { below: apiPos, gap: 56, align: "end" })

The layout keeps the chain of values in progress. When it needs a value that is already in the chain, the placements depend on each other, and the compiler stops with `PLACEMENT_CYCLE` and the chain, such as `position(api) → position(cache) → position(api)`. The route of an edge is in the chain too, because a frame's rectangle can depend on it.

### Three rectangles of a shape

The compiler uses three rectangles for each shape, as <Ref to="dc-boxes" /> shows. The **layout bounds** are the position and size, and placement uses them. The **outline** is the shape as drawn, such as the rhombus of a decision, and edges attach to it. The **ink bounds** cover everything painted. They differ from the layout bounds only for a start or end with a label beside its dot. A document's wave dips below its layout bounds by 5 units, which the ink bounds leave out. The outline of a stack of replicas leaves two corners of its layout bounds empty. The label lies outside the layout bounds, so it does not move the dot off the axis of its column. Enclosures, the overlap checks, and the view box use the ink bounds.

## Edges

Routing turns each edge into a list of points, its arrowheads, and its label boxes. An edge that ends at an element attaches to the element's outline. An edge that ends at a point, such as `api.bottom`, ends exactly there.

**[Direction](directions):** a brace is an edge style, as in `d.line(a, b, { style: "brace" })`. A brace is therefore an edge, and its labels, id, steps, and checks work as they do for every edge.

### Routes

Each edge has one route, which carries all of its geometry between the two ends. The route is one of these forms, and the compiler adds the corners or the curve that the form needs:

- `"straight"`: one line. It is the default.
- `"hv"` and `"vh"`: one elbow, across first or down first.
- `{ viaX: x }` and `{ viaY: y }`: a channel at a given x or y. The value is a number, or anything `via` takes, of which the channel uses the x or the y. An element stands for its center.
- `{ via: [points] }`: a list of points.
- `{ bend: units }`: a curve that bows this many units to the left of the direction of travel. A bend of 0 is straight.
- `{ loop: side }`: a loop that leaves and returns on one side of an element.

An edge goes from an element to itself when both ends are the same element. Ends given as points on one element, such as `a.top` and `a.bottom`, are two points, so that edge is routed between them like any other. An edge from an element to itself has the route `{ loop: "right" }` unless it gives a `loop` route, and only such an edge takes `loop`. <Ref to="dc-routes" /> shows the forms.

<Diagram id="dc-routes" caption="The route forms, a curve, and loops." draw={(d) => {

Each shape gives the outline that edges attach to as a polygon, made by the same functions that draw it, so an edge cannot end off the ink. Curves, such as the caps of a cylinder, are sampled into short legs. A box gives its bounds, since its rounded corners are small, and so do an enclosure and a frame. A stack of boxes or pages gives the outline of all its shapes together. It steps in at the top-left and bottom-right corners of the bounds, and along the bottom it follows the front page's wave and, right of it, the waves of the pages behind. The middle of each side of the bounds lies on it: the top and the right on the shape at the back, the left and the bottom on the front one. A start or an end attaches to its circle, and a record's cell as [records](#records-and-marked-text) describe.

A straight edge attaches where the line from the element's center toward the other end leaves the outline. Where a polygon has notches, it is the last place the line leaves it. An edge with corners attaches on the side of the bounds that faces its adjacent route point. On that side it takes the projection of that point, or the middle of the side when the projection falls outside the side less the corner radius. It attaches where the line through that point at a right angle to the side meets the outline, so it leaves the element at a right angle, also on a decision or a start. For `hv`, `vh`, `viaX`, and `viaY`, the adjacent point lines up with the center, so these attach at the middle. An edge whose ends coincide is `DEGENERATE_EDGE`.

A grid's gutters give `viaX` and `viaY` their channels. A gutter is a point in the middle of the gap after a column or a row, counted from 0, at the grid's center on the other axis. The layout evaluates it from the grid's tracks, like any other point. A gutter after the last track, or before the first, has no gap: the draw program records it as `UNKNOWN_GUTTER`, and the point stands at the grid's center so the compile goes on.

In the running example, `client->api` is straight. Both elements are at the same height, so the line between their centers leaves Client at its right side, at (104, 23), and meets API at its left side, at (192, 23).

### Labels

An edge has no label, one, or a list of them, all given when the edge is made. A label stays horizontal and sits on one straight piece of the finished route: by default the longest, at its middle, above a horizontal piece and to the right of a vertical one. `segment` names the piece, `along` the position on it from 0 to 1, and `side` the side of the piece where the label sits: `top`, `bottom`, `left`, or `right`, the sides that ports and loops name. `top` puts the label above the piece. A curve or a loop puts its labels outside it. A label on a single straight edge must fit between the two ends, or the compiler reports `LABEL_CROWDED`. Labels on other routes are covered by [the overlap checks](#checks).

In the running example, "request" sits above the middle of its edge, centered at x = 148, and "query" sits to the right of the vertical edge.

### Arrowheads

Each end of an edge has an arrowhead kind: `head` at the `to` end and `tail` at the `from` end. The kinds are `filled`, `open`, and `none`. `d.arrow` has a filled head and no tail, and `d.line` has neither, unless the options say otherwise. The two calls differ only in these defaults, so an edge with two heads is `d.arrow(a, b, { tail: "filled" })`. A sequence gives a call a filled head, a reply and an async message an open head, and a lifeline none. A tree's lines have none unless its `edge` option gives `head` or `tail`.

A head points along the last straight piece at its end, with its tip on the end point. The line is shortened into each head, so the stroke does not show past the tip. An end without a head keeps its full length. In the running example, the line of `client->api` ends at x = 186.5, and the tip of its head is at x = 192.

The piece that carries a head is the last leg of a route with corners, and the whole curve of a bent edge. The compiler samples a curve into short legs, and the head points along the last of them. A head is 10 units long and needs a piece of at least 17 units, because it takes at most 60% of the piece. On a shorter piece, the head shrinks to fit, and the compiler reports `HEAD_CROWDED` for that end, with the room the head has and the room it needs. Its subject is `head` or `tail`, so the two ends of one edge are two diagnostics.

**[Direction](directions):** the arrowhead kinds also include a hollow triangle, a filled and a hollow diamond, and crow's foot ends, which class and ER diagrams use. The compiler then writes each head as path data with a fill mode, because the crow's foot for zero has a circle.

## Records and marked text

The cells of a record and the marks of a text are elements of their own, so edges, steps, and links treat them like any other element. A draw program reaches one with its parent's `member()` and its own id, such as `rec.member("payload")`, and a missing one is `UNKNOWN_ELEMENT`, with its parent standing in. Their rectangles come from their parent's rectangle. A ruler's functions run when the record is measured, after the ids are final. A function that throws or gives anything other than text or a number is `INVALID_ARGUMENT` about the record, with the subject `ruler.top` or `ruler.left` and a message that names the first such column or row; that label is empty, and the rest of the record is drawn. <Ref to="dc-record" /> shows a record; the [structures reference](https://github.com/tsaarni/yapparatus/blob/main/starter/docs/diagram-structures.md) lists the forms.

The grid lays out a record's cells row by row on equal columns, as wide as the widest text needs. A cell can span several columns, and a cell that starts a row and spans a multiple of the row covers several rows, as Payload does. A cell that does not fit in its row is `CELL_SPAN`.

An edge at a cell attaches at the middle of a side on the record's outline, so that it crosses no other cell. A cell with no such side, such as Flags, cannot take an edge without crossing its neighbors, so a pin gives it a numbered badge that a note can refer to.

A mark highlights words or lines of a text. The compiler finds the marked words in the measured lines and computes their rectangle from the measured widths. Words that do not occur exactly once on one line are `MARK_UNMATCHED`. Lines are a line number from 1, or the first and the last line, such as `[2, 4]`. The signature checks that they are whole numbers of 1 or more, and the compiler that they lie within the measured lines with the first not after the last; lines that do not are `MARK_UNMATCHED`.

## Sequences

A sequence diagram is built from the other elements while the draw program runs, so the layout and the checks treat it like any other drawing. `d.sequence` takes the participants and a list of entries, called `messages`, in which each entry is a message, a note, or a fragment. A fragment and each of its `else` branches hold such a list too. The participants go into a row. The messages are then laid out in time order, each one lower than the last, as edges between two points, one row apart; the option `rowHeight` sets a row's height. A bar means that a participant is handling a call, so only a receiver gets one. A call opens an activation bar on its receiver. A reply closes the bar of the latest open call from the participant it returns to, and closes every call made after that one. A call that no reply closes gets a short bar, and an async message gets none. Sending opens no bar: a participant that only sends has a plain lifeline, and its messages start and end on it. A self-message on a participant with no bar starts from the lifeline and opens only its own short bar. Lifelines and bars are drawn, but the checks and the steps leave them out. A step focuses a message only when it names the message or a fragment that holds it, never through its two participants, because two participants exchange many messages and each is its own moment.

A reply with no open call from the participant it returns to is `REPLY_WITHOUT_CALL`, a warning, with the fix: swap `from` and `to`, or remove `reply`. The reply is drawn and closes no bar. The branches of a fragment are alternatives, so a reply in an `else` branch may also answer a call that was open when the fragment began, which an earlier branch's reply already closed: in an `alt`, each branch replies to the same call. A message from a participant to itself is drawn as a call, so its `reply` is ignored and never reported as a reply without a call.

**[Direction](directions):** the compiler matches replies to calls more strictly. `REPLY_WITHOUT_CALL` and the activation bars use one matching, per participant and across the branches of a fragment, so the stricter matching also changes where the bars end.

A message, a note, and a fragment take the options of every drawn element: `id`, `role`, `category`, and `stepOnly`. A message's id comes from its label, a note's from its text, and a fragment's from its operator and title, as for a frame. A message is an edge, and it takes `dashed` too. `reply` and `async` set a message's line and arrowhead: a reply has a dashed line and an open head, and an async message an open head. An explicit `dashed` sets the line of any message. A step-only message is an edge that only the steps that focus it show, and its activation bar follows it, so the bar appears with it. A step-only note is a step-only shape. A step-only fragment is a step-only frame: the steps that focus it show the frame, and its messages are step-only only when they say so themselves.

A message or a note about a shape that is not a participant is `UNKNOWN_PARTICIPANT`. An entry that is not a message, a note, or a fragment, a message without a label, and a message with both `reply` and `async` are `INVALID_ARGUMENT`, as the signature of `d.sequence` states. The sequence skips each entry it cannot draw and draws the rest, and a message with both `reply` and `async` keeps the first of the two. The diagnostic's subject is the entry's place in the list, such as `messages[2].label`. `d.sequence` returns the column that holds the sequence: the row of participants and a spacer, an empty shape as tall as the lifelines, so that an element placed below the sequence clears them.

A fragment is a frame whose corners the sequence sets from its participants, before anything is measured, so its members can reach past them: a self-message at the rightmost participant has its label to the right of that participant. The scene lists the members of each fragment: its messages, its notes, and the fragments inside it. A frame is an element, so the layout gives its rectangle when something first needs it, as for any element. A frame with members covers their ink: edge points, heads, and labels, node rectangles and labels, and inner frames. Where a member reaches past the corners, the frame keeps a margin of 8 units around it. An outer frame covers the rectangle of an inner frame, which the layout computes first. A frame's anchors, ports, and outline come from this final rectangle. An edge among a frame's members that also ends at the frame therefore depends on itself, which is `PLACEMENT_CYCLE` with a chain such as `route(a->loop) → bounds(loop) → route(a->loop)`. A frame that an author draws with `d.frame` has no members and lies exactly between its corners.

**[Direction](directions):** a sequence also takes three more kinds of entry: a found or lost message, which starts or ends at the edge of the diagram; a message that creates or destroys a participant; and a `ref` fragment, which refers to another sequence.

## Trees

A tree is also built from the other elements while the draw program runs: rows, columns, and lines. It adds no position owner, so the layout and the checks treat it like any other drawing. Each node with children becomes a container of the node and its children's subtrees, and a leaf stays a bare node. The layout sets the containers:

- `down`: a column of the node and a row of its subtrees, top-aligned. Each line leaves the node's bottom and turns at the column's gutter, halfway between the levels.
- `right`: a row of the node and a column of its subtrees, left-aligned, with each line turning at the row's gutter.
- `both`: at the root, a row of a column of left subtrees, the root, and a column of right subtrees. The root's children alternate right and left. A left subtree is `right` mirrored: its column comes first and is right-aligned, so deeper levels keep growing away from the root.
- `indent`: a column of the node and a grid whose rows each hold an empty cell and one subtree, so the gap after the empty column indents every subtree by the same amount. Each line starts at a point under the left part of the node's rectangle, goes down, and turns into the child's left side.

Any other layout is `INVALID_ARGUMENT`, and the tree grows `down`.

A container centers its node across the container, so a node is centered on the whole of its subtrees, not on its direct children. Adding a child widens its ancestors and moves nothing else.

Every line from one parent starts at the same point and runs down or across the same trunk before it turns to its child, so two lines share a stretch from their first points and part. That is a fork, which the `EDGE_OVERLAP` check allows. The lines are ordinary edges, so the other checks apply to them as to any edge. A node that already has a position owner is `CONFLICTING_PLACEMENT` when the tree puts it in a container, as in any row or column.

A container's id is its node's final id followed by `-tree`, and the row, column, or grid of the node's subtrees is the node's id followed by `-children`. In the `both` layout, the two columns beside the root are the root's id followed by `-left` and `-right`. The tree's `id` names the outermost container in place of the root's id followed by `-tree`. These ids are derived from the node's, so a repeated one gets a number, as any derived id does. The scene lists each container's lines as its members, and a container lists its node and its inner row, column, or grid. A step that focuses a container therefore focuses the branch below it: its nodes, its lines, and the lines of every subtree in it. The line into the branch belongs to the parent's container, and a step that focuses the parent and the branch focuses it too, as it does any edge whose two ends it focuses.

## Roles and categories

The compiler gives every element a role and at most one category. The web app and the picture turn them into colors and strokes, as [the components page](components#roles-and-categories) shows.

An element keeps its own role, or the default role, and an enclosure without a role is `muted`. A frame without a role has no role in the compiled diagram and keeps its own look: a hairline in the control border color, its labels in the text color, and its tab on the raised surface. No role draws that, because `default` has a heavier line and `muted` another color and no fill. A role replaces the look, and a category changes its colors only, as on any element. The shapes of a stack of replicas are one element: they share its role and category, and a step focuses and fades them together. Each one is drawn over a cover in the figure's color, from the back, so it hides the ones behind it, also in the `muted` role, which has no fill. More than one element with the `accent` role is `ACCENT_OVERUSED`.

Categories are numbered 1 to 4 in the order the draw program first uses them, and each number has its own color. A fifth category is `TOO_MANY_CATEGORIES`, and its elements get no color. The legend lists the categories, and a step that focuses a category's id focuses all its elements.

## Checks

Each stage reports the problems it finds, as <Ref to="dc-check-origins" /> lists. Each message names the elements involved and says how to fix the problem, as [diagnostics](/diagnostics#codes-and-severity) describes. The registry of codes lists every diagram code with its severity and meaning.

**[Direction](directions):** a diagnostic about an element names the page line of the call that created the element and the page line of the call that placed it. The compiler receives a function that gives the page line of each call, as it receives the font measure. The page compiler keeps a table from element id to page line, outside the compiled diagram. Elements that a helper function or a loop creates share a page line.

### Collisions

The collision checks run on the exact geometry, before rounding. Two rectangles overlap only when they share more than half a unit in both directions, and an edge hits a shape only when it passes more than one unit inside it. Shapes that touch, and an edge that ends on an outline, are therefore not reported. Edges also keep eight units away from enclosure titles.

The checks report conflicts between elements that the user sees as separate. They skip a cell or mark and its parent, lifelines and activation bars, and pairs of step-only elements, which the step checks compare. A step-only enclosure is one of such a pair with a step-only shape inside its boundary or a step-only edge across its title. Free text is checked like any shape, because it has no fill and an edge through it shows through the words. An edge is checked against its own ends too, except on the leg that touches each end, so a route that runs through its own end is `EDGE_NODE_INTERSECTION`. The compiler reports it and does not repair it. A cell and its record count as one end, and an edge whose two ends are on one element, or that has a `bend` route, is not checked against its ends.

Two edges that share a stretch of line longer than 4 units, within half a unit, read as one line, and the compiler reports `EDGE_OVERLAP`. It compares the routes before the arrowheads shorten them, so two identical curves are caught too, because their legs coincide. A fork or a merge reads correctly and is allowed: the edges run the shared stretch in the same direction, it starts at the first point of both routes or ends at the last point of both, and both routes go on past it. Edges in opposite directions, edges with different ends that share a channel such as a grid's gutter, and an edge that lies wholly on another are reported. The fixes are the route `{ bend: units }`, a `port()`, an offset from a shared gutter, or, for two edges in opposite directions, one edge with `tail: "filled"`. Passive edges, such as lifelines, and pairs of step-only edges are not compared.

### Steps and width

The step checks run on the finished diagram, so they see the final ids. Each id in a step's `focus` must name an element, a container, or a category, or it is `UNKNOWN_ELEMENT`. The message lists the figure's ids. The elements a step focuses are the ids it names, with each container and category replaced by itself and what `groups` lists for it, and then each edge whose two ends are among them. An edge follows its ends when each end is an element or a point taken from that one element alone: an anchor, a port, or an offset of either, offsets of offsets included. A cell or a mark is an end of its own, which focusing its record or text includes. A point made with `xy`, `lerp`, a gutter, or `[x, y]` combines elements or names none, so it is free. An edge with a free point at an end, a step-only edge, a sequence message, and a decoration such as a lifeline do not follow their ends, so a step names them. A step without `focus` shows the whole figure plain, as with no step open, and step-only elements are absent; for every other purpose it focuses nothing, so it is not the first step that focuses anything under `build`, it counts for neither `STEP_ONLY_UNUSED` nor `BUILD_NEVER_FOCUSED`, and a click or an address never opens it. The step checks, the web app's view, a click on an element, and an address all compute a step's elements in this one way. Shapes, cells, marks, edges, enclosures, and frames can be step-only, and so can the messages, notes, and fragments of a sequence, which are edges, shapes, and frames. Every step-only element must appear in some step, or it is `STEP_ONLY_UNUSED`. With `build`, a shape at an end of an edge that follows its ends must be focused by some step, or it is shown faded from the first step, which is `BUILD_NEVER_FOCUSED`. A member counts as its record or text. A shape with no such edge, an enclosure, a frame, and a grid may stay as scenery. Two step-only shapes that one step shows together must not overlap. A step-only shape that is not a member of a step-only enclosure that the same step shows must stay outside its boundary, and a step-only edge must not cross its title.

The width check reports `DIAGRAM_SCROLLS` for a diagram wider than a fixed limit: the width of the widest figure area divided by the smallest scale the web app shrinks a diagram to.

The limit does not depend on any window, so the result is the same on every screen.

## The compiled diagram

The compiled diagram, `CompiledDiagram`, holds what the web app and the picture need to draw, and nothing that only the compiler uses.

A node names its shape by the call that makes it, such as `decision`, `start`, or `end`. Shapes, edges, enclosures, and frames hold their final geometry: rectangles, points, and text lines with their positions and fonts. Each one carries its role, the slot of its category, and whether it is step-only; a frame without a role carries none. The web app, the picture, and print leave out a step-only element outside the steps that focus it, whatever its kind. The compiled diagram lists nodes in paint order: decorations first, then the author's elements in creation order. Decorations are the elements that the checks and the steps leave out, such as activation bars, so a note over a bar covers it. `groups` lists, for each container and category, the elements that a step focuses with it. `icons` holds the markup of each icon that a node names, once, as the icon package gives it: elements on a 24 unit grid that paint in `currentColor`. A node with an icon names it and gives the icon's rectangle. The table holds only markup from the package; the author's text never reaches it. Each icon's markup is in the table once however many nodes use it, and a typical icon's markup is about 250 bytes. `ok` and `diagnostics` say whether the diagram can be drawn and what is wrong with it. An edge that follows its ends names the elements at them in `ends`, so the web app and the step checks apply the steps' rule from the compiled diagram alone; the field costs about 30 bytes an edge. An edge gives its arrowheads as `head` and `tail`, each with its kind and its points, and leaves out an end without one, so the web app and the picture draw each end by itself: a filled head as a polygon, an open head as a polyline. <Ref to="dc-compiled-edge" /> shows one edge of the running example.

Every browser downloads the compiled diagrams of a page with its JavaScript, so the last stage keeps them small. It rounds every number to hundredths of a unit, once, after the checks. It also computes the view box: everything painted, with a margin, rounded outward to whole units.

## Pictures

A picture is a PNG of a diagram that the server draws for the agent. The agent asks for it with [`savePicture`](agent-library#savepicture), through [the figures resource](rest-api#read-a-picture), and [the server](server#pictures) draws it from the compiled diagram of the page as it is on disk. <Ref to="dc-picture" /> shows how.

<Diagram id="dc-picture" caption="How the server draws a picture: an SVG from the compiled diagram, then a PNG by resvg." draw={(d) => {
  const compiled = d.box("Compiled diagram", { id: "compiled" })
  const svg = d.box("SVG writer", { sub: "no fonts, no stylesheets", id: "svg" })
  const resvg = d.box("resvg", { sub: "2 pixels per unit", id: "resvg" })
  const png = d.box("PNG", { role: "accent", id: "png" })
  d.equalSize([compiled, svg, resvg, png])
  d.row([compiled, svg, resvg, png], { gap: 56 })
  d.arrow(compiled, svg)
  d.arrow(svg, resvg)
  d.arrow(resvg, png)
  const paint = d.box("Light theme values", { sub: "for each role and category", id: "paint" })
  const glyphs = d.box("Glyph outlines", { sub: "from the web app's fonts", id: "glyphs" })
  d.place(d.row([paint, glyphs], { gap: 32, id: "inputs" }), { above: svg, gap: 56 })
  d.arrow(paint, svg)
  d.arrow(glyphs, svg)
}} />

The SVG writer writes one SVG document that needs no fonts and no stylesheets. It draws the same layers in the same order as the web app, with the same shape outlines, and adds a legend below. An icon is a nested `svg` element at the icon's rectangle, with the icon grid as its view box and a color as its `color`: the label's on a box, and the element's ink on an icon shape, as an actor's figure. The markup's `currentColor` takes that color, and its stroke widths scale with the icon. resvg draws it as a browser does. The picture shows the diagram with no step open. It paints each role and category with the same theme tokens as the web app, resolved to the light theme's values, so every agent gets the same picture. Text is drawn as glyph outlines from the web app's font files, so it is exactly as wide as the compiler measured it.

With the `ids` option, the picture also writes each element's id beside it and outlines the elements that diagnostics name. The server passes the SVG to resvg at two pixels per unit, so that small text stays legible to a model.

## Design decisions

The draw program states the arrangement, and the compiler measures it. Automatic graph layout, as in Graphviz or ELK, can rearrange the whole diagram when one edge is added. A language model states an arrangement well and computes coordinates poorly, so a draw program states rows, columns, and placements, and the compiler computes every number.

The compiler reports problems and does not repair them. A silent repair, such as moving a shape to remove an overlap, hides the problem, changes what the draw program says, and can be undone by the next edit. A stand-in for a value that a call cannot use is always reported as an error. It exists only so that the rest of the figure compiles and one compile reports every problem.

A draw program is JavaScript, and the compiler checks every call when it runs. A text language such as Mermaid, D2, or PlantUML is shorter for simple graphs, but it has no loops, variables, or functions, and its errors are vague. Type-checking the program would add a second kind of error, without element ids, beside the diagnostics. The checks of the calls find the same mistakes while the program runs, so every problem is a diagnostic that names its elements. A program that throws names the page line of the statement.

An element's id never comes from its variable. Graphviz, Mermaid, and D2 name a node by an identifier, and authors expect the same here, but a variable is a name in code: it changes in a refactoring, it may be camelCase, which ids do not allow, and the address a reader comments on would then depend on it. One rule, the `id` option or else the label, keeps every id visible in the call that makes the element. Authors still write a variable in a step when an example's variables and ids are the same word, so the examples in the diagram reference give their elements variables that differ from their ids.

Diagrams compile on the server, so their diagnostics are known as soon as the page compiles, and a build carries data instead of programs. The cost is that the server measures text from the font files.

Pictures are drawn by resvg inside the server process. A headless browser would draw the web app's own SVG exactly, but it is a large dependency and takes seconds to start for one image.
