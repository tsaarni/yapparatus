# Diagram compiler

This page describes how the diagram compiler turns a draw program into a compiled diagram, and how the server draws a picture from it. How the web app shows a compiled diagram is on [the components page](components#diagram).

## Overview

The page compiler finds each `<Diagram>` on a page and [hands its draw program to the diagram compiler](page-compiler#diagrams), together with the ids and focus lists of its steps. The diagram compiler runs in the server. It records what the draw program creates, measures the text, sizes and places every element, routes the edges, checks the result, and returns a compiled diagram: plain data with every coordinate in it. <Ref to="dc-stages" /> shows the stages.

The compiler measures, sizes, and places on demand: it computes a value the first time a later stage asks for it, and keeps it. The order in <Ref to="dc-stages" /> is the order in which results become final.

A stage reports each problem it finds and continues with a usable value, so one compile reports all problems at once. Only a placement cycle or an exception stops the compile, and the result then has no geometry. A diagram with any error is marked as failed, and the server draws no picture of it.

## The scene

The draw program receives an object `d` whose functions record elements and arrangements, which together are the scene. A function that creates an element returns an object that stands for it, and the program passes it to later calls, such as a row or an edge. <Ref to="dc-scene" /> shows the scene of the running example.

<Diagram id="dc-scene" caption="The scene that the running example records: each element and what sets its position." draw={(d) => {
  d.record([
    "client\tbox\tin row-1",
    "api\tbox\tin row-1",
    ["database\tcylinder\tbelow api", { id: "db-place" }],
    "row-1\trow\tnothing: the origin",
    "client->api\tedge\tfrom client to api",
    "api->database\tedge\tfrom api to database",
  ], { title: "Scene", header: "id\tkind\tposition", mono: true, id: "scene" })
}} />

A scene holds at most 2,000 elements, counting nodes with their cells and marks, edges, frames, rows and columns, and enclosures. The checks compare elements in pairs, so a larger scene would take minutes to check. The call that would create one more element throws, which is `DRAW_FAILED`.

An element in the scene has no coordinates. A point on it, such as `api.bottom`, or a point computed from others, such as `api.bottom.offset(0, 20)`, is a description that the layout evaluates once the positions it names are known. The order of the statements therefore does not matter.

Each element gets its position from exactly one source: the row or column it is in, or the `place()` call that places it. A second source is `CONFLICTING_PLACEMENT`, and the first one stays in force. Before layout, the compiler looks for elements with no source. The first one goes to the origin, and every other one is reported as `UNPLACED`. In the running example, only the row has no source, so it is at the origin.

Rows and columns can be placed like any element, so they nest.

## Ids

Every element has an id. The page uses it as the element's address, `/page#figure--element`, and steps, diagnostics, and references refer to elements by it. An element may have an explicit `id`. Without one, the compiler derives an id, as <Ref to="dc-ids" /> lists.

<Table id="dc-ids" caption="Derived ids.">

| Element | Derived id | Example |
|---|---|---|
| A shape with a label | The label as a slug: lowercase, with hyphens for everything else | `"Auth service"` → `auth-service` |
| A row or column | The direction and its count among rows and columns | `row-1`, `column-2` |
| An enclosure | Its title as a slug, or `boundary` and its count | `backend`, `boundary-1` |
| An edge | The ids of its two ends, joined by `->` | `client->api` |
| A cell or a mark | The parent's id, a dot, and its own name as a slug | `users.team-id` |
| A category | Its name as a slug | `to-be-removed` |

</Table>

The id check makes the ids final before layout. A repeated explicit id is `DUPLICATE_ID`, and a repeated derived id gets `-2`, `-3`, in the order of creation. Cells, marks, and edges are settled last, because their ids are built from the final ids of their parents and ends.

A derived id changes when its label changes. The link check verifies only the figure part of an address, so the [diagram reference](https://github.com/tsaarni/yapparatus/blob/main/starter/docs/diagrams.md#ids) asks for an explicit id on any element that something outside points at.

## Text measurement

Text measurement splits each label into lines, and wraps them at word boundaries when the shape has a fixed `width`. Every line in the compiled diagram carries its font size and weight, and the web app and the picture draw it with exactly those values.

The widths come from the font measure, which reads the font files and `@font-face` rules that the web app loads. For each character, it picks the face that a browser picks, and it shapes the text with fontkit. A browser test checks that its widths are within 0.5 pixels of the browser's own. A character that no face has gets a width of one em and is reported as `FONT_FALLBACK`, because a browser draws it in a system font of unknown width.

## Layout

The layout answers three questions about any element: its size, its position, and its rectangle, which combines the two. Sizes are computed from the inside out, and positions from the outside in.

### Sizes

A shape's size is its measured text plus padding on each side, and at least a minimum size. A fixed `width` or `height` replaces it. Shapes in a size group, such as `equalSize`, take the largest size in the group, fixed sizes included. A member with a fixed size on an axis of the group keeps it, and its text wraps at that width. When that size is smaller than the group's, the group is not equal, and the compiler reports `FIXED_SIZE_IN_GROUP`. A row is as wide as its children and the gaps between them, and as tall as its tallest child; a column is the same on the other axis. An enclosure surrounds its members with padding and a band for its title.

In the running example, "Client" measures 38.0 by 18.6. With the padding, the box would be 70 by 40.6, so the minimum size of 104 by 46 applies. The cylinder adds 7.3 units of cap above and below its text and is 55.2 units tall.

### Positions

A position is the top-left corner of an element's rectangle. A child of a row or column sits after the children before it, one gap apart. An element placed with `place()` sits at the gap from the rectangle of the element it names, or puts its anchor on the point it names.

<Ref to="dc-resolve" /> shows the values that the layout computes to place the database in the running example. Each is computed once, the first time it is needed.

### Three rectangles of a shape

The compiler uses three rectangles for each shape, as <Ref to="dc-boxes" /> shows. The **layout bounds** are the position and size, and placement uses them. The **outline** is the shape as drawn, such as the rhombus of a diamond, and edges attach to it. The **ink bounds** cover everything painted. They differ from the layout bounds only for a start or end with a label beside its dot. The label lies outside the layout bounds, so it does not move the dot off the axis of its column. Enclosures, the overlap checks, and the view box use the ink bounds.

## Edges

Routing turns each edge into a list of points, its arrowheads, and its label boxes. An edge that ends at an element attaches to the element's outline. An edge that ends at a point, such as `api.bottom`, ends exactly there.

### Routes

Each edge has a route form, and the compiler adds the corners that the form needs between the two ends. <Ref to="dc-routes" /> shows the forms: a straight line, one elbow, a channel at a given x or y, a list of points, a curve, and a loop.

A straight edge attaches where the line from the element's center toward the other end leaves the outline. An edge with corners attaches on the side that faces its adjacent route point, at the projection of that point onto the side, so it leaves the element at a right angle. When the projection falls outside the side, less the corner radius, the edge attaches at the middle of the side; on a diamond, a dot, or a ring it always does. For `hv`, `vh`, `viaX`, and `viaY`, the adjacent point lines up with the center, so these attach at the middle. An edge whose ends coincide is `DEGENERATE_EDGE`.

In the running example, `client->api` is straight. Both elements are at the same height, so the line between their centers leaves Client at its right side, at (104, 23), and meets API at its left side, at (192, 23).

### Labels

A label stays horizontal and sits on one straight piece of the finished route: by default the longest, at its middle, above a horizontal piece and to the right of a vertical one. A label on a single straight edge must fit between the two ends, or the compiler reports `LABEL_CROWDED`. Labels on other routes are covered by [the overlap checks](#checks).

In the running example, "request" sits above the middle of its edge, centered at x = 148, and "query" sits to the right of the vertical edge.

### Arrowheads

A head points along the last straight piece, with its tip on the end point. The line is shortened into the head, so the stroke does not show past the tip. In the running example, the line of `client->api` ends at x = 186.5, and the tip of its head is at x = 192.

## Records and marked text

The cells of a record and the marks of a text are elements of their own, so edges, steps, and links treat them like any other element. Their rectangles come from their parent's rectangle. <Ref to="dc-record" /> shows a record; the [structures reference](https://github.com/tsaarni/yapparatus/blob/main/starter/docs/diagram-structures.md) lists the forms.

  const outline = d.note("A cell on the outline", { id: "outline-note" })

The grid lays out a record's cells row by row on equal columns, as wide as the widest text needs. A cell can span several columns, and a cell that starts a row and spans a multiple of the row covers several rows, as Payload does. A cell that does not fit in its row is `CELL_SPAN`.

An edge at a cell attaches at the middle of a side on the record's outline, so that it crosses no other cell. A cell with no such side, such as Flags, cannot take an edge without crossing its neighbors, so a pin gives it a numbered badge that a note can refer to.

A mark highlights words or lines of a text. The compiler finds the marked words in the measured lines and computes their rectangle from the measured widths. Words that do not occur exactly once on one line are `MARK_UNMATCHED`.

## Sequences

A sequence diagram is built from the other elements while the draw program runs, so the layout and the checks treat it like any other drawing. The participants go into a row. The messages are then laid out in time order, each one lower than the last, as edges between two points. A bar means that a participant is handling a call, so only a receiver gets one. A call opens an activation bar on its receiver. A reply closes the bar of the latest open call from the participant it returns to, and closes every call made after that one. A call that no reply closes gets a short bar, and an async message gets none. Sending opens no bar: a participant that only sends has a plain lifeline, and its messages start and end on it. A self-message on a participant with no bar starts from the lifeline and opens only its own short bar. Lifelines and bars are drawn, but the checks and the steps leave them out.

## Roles and categories

The compiler gives every element a role and at most one category. The web app and the picture turn them into colors and strokes, as [the components page](components#roles-and-categories) shows.

An element keeps its own role, or the default role, and an enclosure without a role is `muted`. More than one element with the `accent` role is `ACCENT_OVERUSED`.

Categories are numbered 1 to 4 in the order the draw program first uses them, and each number has its own color. A fifth category is `TOO_MANY_CATEGORIES`, and its elements get no color. The legend lists the categories, and a step that focuses a category's id focuses all its elements.

### Collisions

The collision checks run on the exact geometry, before rounding. Two rectangles overlap only when they share more than half a unit in both directions, and an edge hits a shape only when it passes more than one unit inside it. Shapes that touch, and an edge that ends on an outline, are therefore not reported. Edges also keep eight units away from enclosure titles.

The checks report conflicts between elements that the user sees as separate. They skip a cell or mark and its parent, lifelines and activation bars, and pairs of step-only elements, which the step checks compare. An edge is checked against its own ends too, except on the leg that touches each end, so a route that runs through its own end is `EDGE_NODE_INTERSECTION`. The compiler reports it and does not repair it. A cell and its record count as one end, and a self-loop or a bent edge is not checked against its ends.

### Steps and width

The step checks run on the finished diagram, so they see the final ids. Each id in a step's `focus` must name an element, a container, or a category, or it is `UNKNOWN_ELEMENT`. Every step-only element must appear in some step, and two that one step shows together must not overlap.

The width check reports `DIAGRAM_SCROLLS` for a diagram wider than a fixed limit: the width of the widest figure area divided by the smallest scale the web app shrinks a diagram to.

The limit does not depend on any window, so the result is the same on every screen.

## The compiled diagram

The compiled diagram, `CompiledDiagram`, holds what the web app and the picture need to draw, and nothing that only the compiler uses.

Shapes, edges, enclosures, and frames hold their final geometry: rectangles, points, and text lines with their positions and fonts. The compiled diagram lists nodes in paint order: decorations first, then the author's elements in creation order. Decorations are the elements that the checks and the steps leave out, such as activation bars, so a note over a bar covers it. `groups` lists, for each container and category, the elements that a step focuses with it. `ok` and `diagnostics` say whether the diagram can be drawn and what is wrong with it. <Ref to="dc-compiled-edge" /> shows one edge of the running example.

## Pictures

A picture is a PNG of a diagram that the server draws for the agent. The agent asks for it with [`savePicture`](agent-library#savepicture), through [the figures resource](rest-api#read-a-picture), and [the server](server#pictures) draws it from the compiled diagram of the page as it is on disk. <Ref to="dc-picture" /> shows how.

<Diagram id="dc-picture" caption="How the server draws a picture: an SVG from the compiled diagram, then a PNG by resvg." draw={(d) => {
  const compiled = d.box("Compiled diagram", { id: "compiled" })
  const svg = d.box("SVG writer", { sub: "no fonts, no stylesheets", id: "svg" })
  const resvg = d.box("resvg", { sub: "2 pixels per unit", id: "resvg" })
  const png = d.box("PNG", { role: "accent", id: "png" })
  d.equalSize([compiled, svg, resvg, png])
  d.row([compiled, svg, resvg, png], { gap: 56 })
  d.arrow(compiled, svg)
  d.arrow(svg, resvg)
  d.arrow(resvg, png)
  const paint = d.box("Light theme values", { sub: "for each role and category", id: "paint" })
  const glyphs = d.box("Glyph outlines", { sub: "from the web app's fonts", id: "glyphs" })
  d.place(d.row([paint, glyphs], { gap: 32, id: "inputs" }), { above: svg, gap: 56 })
  d.arrow(paint, svg)
  d.arrow(glyphs, svg)
}} />

The SVG writer writes one SVG document that needs no fonts and no stylesheets. It draws the same layers in the same order as the web app, with the same shape outlines, and adds a legend below. The picture shows the diagram with no step open. It paints each role and category with the same theme tokens as the web app, resolved to the light theme's values, so every agent gets the same picture. Text is drawn as glyph outlines from the web app's font files, so it is exactly as wide as the compiler measured it.

With the `ids` option, the picture also writes each element's id beside it and outlines the elements that diagnostics name. The server passes the SVG to resvg at two pixels per unit, so that small text stays legible to a model.

## Design decisions

The draw program states the arrangement, and the compiler measures it. Automatic graph layout, as in Graphviz or ELK, can rearrange the whole diagram when one edge is added. A language model states an arrangement well and computes coordinates poorly, so a draw program states rows, columns, and placements, and the compiler computes every number.

The compiler reports problems and does not repair them. A silent repair, such as moving a shape to remove an overlap, hides the problem, changes what the draw program says, and can be undone by the next edit.

A draw program is TypeScript. A text language such as Mermaid, D2, or PlantUML is shorter for simple graphs, but it has no loops, variables, or functions, and its errors are vague. An error in a draw program names the page line of the statement.

Diagrams compile on the server, so their diagnostics are known as soon as the page compiles, and a build carries data instead of programs. The cost is that the server measures text from the font files.

Pictures are drawn by resvg inside the server process. A headless browser would draw the web app's own SVG exactly, but it is a large dependency and takes seconds to start for one image.
