# Components

This page lists everything a page or a chat reply can contain and shows an example of each item. For each item, it says where its code is, whether it is numbered, what the reader can link to or ask about, and what the compiler checks. How authors write each component is in the authoring reference, [`starter/docs/components.md`](/-/files/yapparatus/starter/docs/components.md).

1. **Every component also works in chat replies,** without imports and with the same line length as the page. In a reply, nothing is numbered and there are no Link or Ask buttons, because a reply is not part of the document.
2. **A failed check is reported by its code.** Each code in the Checks column is an error in the registry, except some diagram and chart codes, which are warnings. The server reports each problem with its file and line. It refuses a reply that contains an error. See [diagnostics](diagnostics#codes-and-severity).
3. **A selection gives more precise context than the buttons.** A selection in a list item or a table row points at that line. See [asking about the page](reader-app#asking-about-the-page).

## Text and Markdown

Headings, paragraphs, lists, links, emphasis, inline code, images, quotations, rules, and tables are ordinary Markdown. [`src/reader/prose.tsx`](/-/files/yapparatus/src/reader/prose.tsx) gives each one its style.

- **Headings** use `##` and `###` only. Both levels are numbered and listed in the contents. A deeper level is an error (`HEADING_DEPTH`).
- **Links** are checked. A link to a page or anchor that does not exist is an error.
- **Tables** align text to the left and numbers to the right. Numbers use tabular figures, which all have the same width. Each header is aligned like its column. With this alignment, the reader can compare values down a column. Long cells keep a readable width. Wrap a table in `Table` to give it a number and a caption.

> A quotation without a marker is an ordinary quotation, like this one.

## Alerts

> [!NOTE]
> A note adds something the reader may want to know.

> [!WARNING]
> A warning is for a step that can lose data or break something.

An alert is a blockquote whose first line is `[!NOTE]`, `[!TIP]`, `[!IMPORTANT]`, `[!WARNING]`, or `[!CAUTION]`. The compiler removes the marker and passes the kind to the reader app, which draws the icon, the title, and the color. Any other marker is an error. The syntax is the same as on GitHub, which agents already know. Replies need no extra component. An alert is one or two sentences.

## Code

Shiki, the highlighter, highlights a fenced code block at build time with the theme colors. The lines of the block do not wrap. The block names a language that Shiki knows, or `text`. Shiki loads a language when a block first uses it.

Code marks show what changed in a block:

```ts
const retry = {
  attempts: 3, // [!code --]
  attempts: 5, // [!code ++]
  delayMs: 200, // [!code highlight]
};
```

The marks are comments at the end of a line. The compiler removes them before highlighting. They show what changed without a second copy of the code. The Copy button copies the code after the change.

**The compiler does not check line length.** Code written for a document should stay within 100 columns, so it fits the breakout track without scrolling. Code copied from a source keeps its formatting, so the reader can compare it with the original.

**Highlighted code has one form.** The compiler turns every code block, excerpt, and whole file into a `HighlightedCode` object, and one reader component, `CodeBlock`, draws it. The object lists each token style once and gives each line as pairs of a style number and a text. Code as a hast tree, the highlighter's own output, takes about 19 times the size of its source; as pairs, it takes under twice the size. A page's code carries the object as a JSON string, which the browser parses faster than code that builds the same object.

## Figures, diagrams, and charts

`Figure` puts a frame around any content, usually an image, and adds a number and a caption below it. A figure is at least as wide as the text. The content is centered, and the caption has the same line length as the text. <Ref to="figure-example" /> frames three icons.

<Figure id="figure-example" caption="A figure that frames icons." description="Three icons in a row: a database, a gateway, and a battery">
  <Icon name="lucide:database" size={32} label="Database" /> <Icon name="local:gateway" size={32} label="Gateway" /> <Icon name="energy-icons:battery-bolt-20" size={32} label="Battery" />
</Figure>

`Diagram` draws a figure from a short program and numbers it like a `Figure`. Every part has an address that the reader can link to and ask about. `Step` children explain the figure in order. <Ref to="diagram-example" /> has two steps. [Diagrams](diagrams) describes the compiler.

  <Step focus="reader">The reader opens the document.</Step>

`Chart` draws data with Observable Plot and numbers it like a `Figure`. Its data is a `Table` on the page, a block of CSV inside it, or a file. <Ref to="chart-example" /> draws a few rows written in the page. [Charts](charts) describes how it works.

## References and icons

`Ref` links to a numbered item or a section and shows its current number. For example, <Ref to="alerts" /> describes alerts. A `Ref` to an id that does not exist is an error.

`Icon` shows an icon from an installed collection or from `icons/`, such as <Icon name="lucide:folder" label="Folder" />. The name is a literal string. The compiler turns it into an import of that one icon. An unknown name is an error.

## Tabs and columns

`Tabs` and `Columns` both hold labelled `Panel`s. Tabs show one panel at a time. The reader picks the panel that applies, such as the form in which a document is read. Columns show every panel side by side, so that the reader can compare them, such as an old and a new design. <Ref to="file-tree-source" /> uses columns to show a source beside its result.

<Tabs>
<Panel label="Live">

```sh
pnpm dev content        # the reader and the chat, on a local server
```

</Panel>
<Panel label="Website">

```sh
pnpm build content      # dist/content/: a static site
```

</Panel>
<Panel label="Single file">

```sh
pnpm build:single content  # dist-single/content/index.html: one offline file
```

</Panel>
</Tabs>

1. **Both containers take the same panels.** An author changes tabs into columns by renaming the outer tag. A reader cannot compare hidden panels, so content to compare belongs in columns.
2. **A tab choice applies to every tab set with the same label.** Choosing a tab selects the tab with the same label in every set, on every page. The browser keeps the choice for the next visit. The reader app matches sets by their labels and uses no group key, so authors have no key to choose or forget. Unrelated sets with the same labels also change together. This is another reason to put a before and an after in columns.
3. **Find in page and print reach hidden panels.** Each hidden panel has `hidden="until-found"`. Find in page reveals the panel and selects its tab in that set only, without changing the reader's choice. Print shows every panel under its label. The tabs follow the WAI-ARIA tabs pattern: the arrow keys, Home, and End move between tabs.
4. **A container is numbered by the figure or listing around it.** Columns alone are not numbered. Code side by side goes in a `Listing`, and drawings side by side go in a `Figure`. The container then takes the full width. A diagram or chart inside a figure is part of it and draws no frame. The compiler reports an `id` or `caption` on it as `FIGURE_NESTED`.
5. **Columns end at the same height.** The last block of each column fills the column's height, so code blocks side by side end together. Up to three columns fit. On a narrow page they stack.
6. **The compiler reads the panels.** It passes their labels to the container, so the container does not inspect its children. It reports these problems:
   - Content outside a panel, or fewer than two panels: `PANEL_CONTENT`.
   - A missing or repeated label: `PANEL_LABEL`.
   - A panel outside a container, or a container inside a panel: `PANEL_NESTED`.
   - More than three columns: `TOO_MANY_COLUMNS`.

## Custom components

A document can import its own React components from `.tsx` files. These components work in that document's pages and use the exported theme. The color samples in [styling](styling#color) are a custom component of this document. Custom components are not available in chat replies, because a reply has no imports. A custom component cannot hold a `Diagram`, because the page compiler compiles only the diagrams written in a page or a reply. See [styling](styling).

## Adding a component

Add a new built-in component in all of these places, in one change:

1. [`src/reader/registry.ts`](/-/files/yapparatus/src/reader/registry.ts), so pages and replies can use it without an import.
2. `pageComponents` in [`src/document.ts`](/-/files/yapparatus/src/document.ts), so the reply check accepts it.
3. The component list in [`src/server/prompt.ts`](/-/files/yapparatus/src/server/prompt.ts), which the agent reads.
4. The authoring guide and [`starter/docs/components.md`](/-/files/yapparatus/starter/docs/components.md).
5. This page: a row in <Ref to="component-inventory" /> and an example.

**Structured content is written as Markdown.** For a component such as `FileTree`, the author writes Markdown, and the compiler turns it into props. Agents write Markdown reliably, and the compiler can check it.
