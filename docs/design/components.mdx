# Components

This page describes how the web app renders the built-in components, with a live example of each.

## Overview

Pages and replies use the built-in components without imports, because the registry of built-in components passes them to every page. <Ref to="components-inventory" /> lists them with the counter that numbers them and the buttons they show.

<Table id="components-inventory" caption="The built-in components.">

| Component | Numbered | Buttons |
|---|---|---|
| Page title `#` | Chapter | Comment |
| Sections `##`, `###` | Section | Link, Comment |
| Markdown text and tables | No | None |
| Alerts | No | None |
| Code blocks | No | Comment |
| `Figure` | Figure | Link, Comment |
| `Table`, `Listing` | Table, Listing | Link, Comment |
| `Excerpt` | No | Comment |
| `Diagram`, `Step` | Figure | Link, Comment, each element |
| `Chart` | Figure | Link, Comment |
| `Ref` | No | None |
| `Icon` | No | None |
| `FileTree` | No | None |
| `Tabs`, `Columns`, `Panel` | No | None |

</Table>

The Link button copies the item's address and needs an `id`. The Comment button exists only in dev mode; see [commenting on the page](web-app#commenting-on-the-page). In a [reply](page-compiler#replies), nothing is numbered and no buttons are shown.

The [page compiler](page-compiler#markdown-conventions) does all parsing: it highlights code, reads excerpts, file trees, and panels, compiles diagrams, and checks chart data. The components only render the result.

## Text and Markdown

Headings, paragraphs, lists, links, quotations, and tables are ordinary Markdown with their own styles. Headings show their [numbers](web-app#numbering-and-references), and the first paragraph after the title is set larger. A link to another site opens in a new tab. A quotation without an alert marker stays a quotation:

> A quotation looks like this.

## Alerts

The page compiler turns a quotation that starts with a marker such as `[!TIP]` into an alert. The web app draws it with an icon, a title, and the kind's color.

> [!TIP]
> A tip suggests a better way to do something.

## Code

Code blocks, excerpts, and the file view share one component. Its bar shows the language, or for an excerpt a link to the file, and a Copy button. Marked lines get a background and a sign in the gutter. Copy leaves out removed lines, so it copies the code after the change:

```ts
const retry = {
  attempts: 3, // [!code --]
  attempts: 5, // [!code ++]
  delayMs: 200, // [!code highlight]
};
```

An excerpt shows the line numbers of its file outside the text, so a selection or a copy takes only the code. With `wrap`, a long line breaks under its own text. A `Table` or `Listing` shows its title above its content.

## Math

The page compiler turns TeX between `$$` marks into MathML; see [math](page-compiler#math). The browser draws it in the system's math font, inline as in $$L_1 > L_2$$, or as a block:

$$
\text{contrast} = \frac{L_1 + 0.05}{L_2 + 0.05}
$$

## Figures

A figure has a frame, a scroll area, and a caption below that starts with its label, such as "Figure 11.1", and ends with its buttons. Diagrams and charts use the same frame. A figure wider than the page scrolls sideways, also with the keyboard. Its accessible name is its `description`, or else its caption. A diagram, chart, or file tree inside a `Figure` draws no frame of its own. <Ref to="components-figure" /> frames three icons.

## Diagram

The web app draws the [compiled diagram](diagram-compiler#the-compiled-diagram) as SVG, with the same shapes as the [picture](diagram-compiler#pictures). Under the drawing are the legend, the step controls, and in dev mode the diagnostics. While a diagram has errors, the web app shows its last good drawing faded above them.

Every element has an address, `figure--element`. In dev mode, a click on an element adds it to the message box.

### Steps

A step focuses some elements, fades the others, and shows a short text under the caption. <Ref to="components-steps" /> has three steps, adds its elements step by step, and has a note that only the second step shows.

<Diagram id="components-steps" caption="A cached read, with three steps." build draw={(d) => {
  const client = d.box("Client")
  const api = d.box("API", { role: "accent" })
  const cache = d.cylinder("Cache")
  const db = d.cylinder("Database")
  d.equalSize([client, api, cache, db])
  d.row([client, api, cache])
  d.place(db, { below: cache })
  d.arrow(client, api, "request")
  d.arrow(api, cache, "lookup")
  d.arrow(cache, db, { id: "miss", label: "miss" })
  const hit = d.note("Most reads stop here", { id: "hit-note", stepOnly: true })
  d.place(hit, { below: api, gap: 48 })
}}>
  <Step focus="client api">The client sends a request to the API.</Step>
  <Step id="lookup" focus="cache api->cache hit-note">The API first looks in the cache.</Step>
  <Step focus="database miss">On a miss, the cache reads the database.</Step>
</Diagram>

A focused element has a heavier line. Focusing a container or a category focuses its elements. A step also focuses an edge whose two ends it focuses, so the first step names only the client and the API, and its arrow comes with them. The second step names `api->cache`, because it focuses only one of its ends. An end counts as an element when it is the element or a point taken from that element alone: an anchor such as `api.bottom`, a port, or an offset of either, such as `api.top.offset(40, 0)` for a parallel edge. An end at a cell or a mark counts as that member, which a step focuses with its record or text. A point that combines elements or names none, made with `xy`, `lerp`, a gutter, or `[x, y]`, never counts. A step-only edge and a sequence message are focused only by a step that names them, since each message is its own moment. Lifelines and activation bars are not part of the rule: a message's activation bar appears with the message.

With `build`, an element stays hidden until the first step that focuses it, and an edge that follows its ends stays hidden while one of them is hidden. A step without `focus` shows the whole figure plain, as with no step open, with or without `build`, and step-only elements are absent. For everything else it focuses nothing, so the other steps hide, fade, and show exactly what they would without it. With `build`, an opening step without `focus` shows the whole figure, and the next step hides what later steps reveal. A step-only element, such as the note, appears only in its steps, on screen and in print. Shapes, edges, enclosures, and frames can be step-only, and so can a sequence's messages, notes, and fragments. The layout is the same in every step.

The view, the step checks, a click on an element, and an address all take a step's focused elements from one computation on the compiled diagram: the ids named, with containers and categories expanded, then each edge whose ends are both among them.

### Interaction

The step controls are previous and next buttons, a counter such as "Step 2 of 3", and Show all, which closes the step. The arrow keys also step, and Escape closes the step. A click on an element, in any mode, opens the next step that focuses it. A step without `focus` is about no element in particular, so a click or an address never opens it.

An address can open a step: [/components#components-steps--lookup](/components#components-steps--lookup) opens the step `lookup`, and an element's address opens the first step that focuses it. In a figure that scrolls sideways, opening a step scrolls the focused elements into view.

### Roles and categories

An element's color comes from its role or its category, which the [diagram compiler](diagram-compiler#roles-and-categories) assigns. <Ref to="components-roles" /> shows every role and two categories.

<Diagram id="components-roles" caption="Roles and categories as the web app draws them." description="A small system with the accent, warning, muted, and external roles, and the categories New and To be removed" draw={(d) => {
  const client = d.actor("Browser", { role: "external" })
  const api = d.box("API", { role: "accent" })
  const cache = d.cylinder("Cache", { category: "New" })
  const search = d.box("Search", { category: "New" })
  const batch = d.box("Batch job", { category: "To be removed", role: "warning" })
  const logs = d.cylinder("Logs", { role: "muted" })
  d.equalSize([api, search, batch])
  d.row([client, api, cache], { gap: 104 })
  d.place(search, { below: api, gap: 64 })
  d.place(batch, { below: cache, gap: 64 })
  d.place(logs, { below: client, gap: 64 })
  d.arrow(client, api, "request")
  d.arrow(api, cache, "lookup")
  d.arrow(api, search, "query")
  d.arrow(batch, cache, { label: "refills", dashed: true })
  d.arrow(client, logs, { label: "logs", role: "muted" })
}}>
  <Step focus="api">`accent` draws the element in the accent color with a heavier outline.</Step>
  <Step focus="batch-job">`warning` draws it in the warning color with a badge.</Step>
  <Step focus="browser logs">`external` draws a dashed outline. `muted` draws a thin line and a muted label.</Step>
  <Step focus="new to-be-removed">A category replaces the color and keeps the role's weight, badge, and dashes. The legend names each category.</Step>
</Diagram>

A role sets the line color, fill, label color, and line weight that every kind of element reads, so a role looks the same on a box, an arrow, an enclosure, and a frame. A frame without a role sets the same four values to its own look: the control border color, the raised surface for its tab, the text color, and a hairline. A frame's line keeps its weight when a step focuses it. The view puts an icon's markup from the diagram's icon table in a nested `svg` at its rectangle, whose text color is the label color on a box and the line color on an icon shape, which has no outline, as an actor's figure. The markup's `currentColor` then follows the role, the category on an icon shape, the theme, and a step's fading. A category sets only the colors, from the theme's four category colors. Focus and pointing add line weight, so weight shows state and color shows meaning.

Pointing at a legend entry highlights exactly its category's elements, without the edges between them that a step would add. In dev mode, an element that a warning names gets a dotted outline.

### Accessibility and print

To assistive technology, a diagram with clickable elements is a group of them, and another diagram is an image. Each element's accessible name is its label. A screen reader reads each step's text when the step opens. Fading and scrolling follow the user's reduced motion setting.

Print shows the plain figure without step-only elements, and prints the text of every step as a numbered list under the caption.

## Chart

The web app loads Observable Plot with the first chart on a page and calls the chart's `plot` with the checked rows and the chart's width. Only the browser draws a chart, so it reports the problems that drawing finds to the server; see [charts](charts#checks-on-the-marks).

## References and icons

A `Ref` shows the current label of its target, such as <Ref to="components-inventory" />, from the targets that [numbering](web-app#numbering-and-references) collects. An unresolved `Ref` shows its text in the style for missing targets.

The page compiler turns each `Icon` into an import of its one SVG file; see [icons](page-compiler#icons). Without `label`, an icon is hidden from assistive technology: <Icon name="lucide:folder" label="Folder" />.

## File trees

The page compiler reads the Markdown list inside a `FileTree` into entries. The web app shows them as nested lists with a folder or file icon, the name, and the comment, as <Ref to="components-file-tree" /> does.

## Tabs and columns

The page compiler passes the labels of the panels to their container, and each `Panel` renders as a tab panel or a column depending on its container.

`Tabs` follows the WAI-ARIA tabs pattern for the keyboard. The browser stores the user's recent choices, and every tab set shows the most recent one it has, so a choice changes every set with that label, on every page and on the next visit. Find in page reveals a hidden panel in that set only. Print shows every panel.

<Tabs>
<Panel label="Dev mode">

```sh
pnpm dev content
```

</Panel>
<Panel label="Website">

```sh
pnpm build content
```

</Panel>
</Tabs>

`Columns` shows the panels side by side, and stacks them on a narrow page. The last block of each column fills its height, so code side by side ends at the same line.

## Custom components

A document can import its own React components from TSX files next to its pages. It styles itself with StyleX and the tokens from `yapparatus/theme.stylex`, as the color swatch in [color](styling#color) does. Replies have no imports, so they cannot use custom components. A `Diagram` inside a custom component fails, because the page compiler compiles only diagrams written in a page or a reply.

## Adding a component

A new built-in component is added in one change, in these places:

1. The registry, so pages and replies can use it without an import.
2. The list of page components that the reply check accepts.
3. The [authoring guide](https://github.com/tsaarni/yapparatus/tree/main/starter/docs) and its component reference.
4. This page: a row in <Ref to="components-inventory" />, a section, and a live example.

A component that takes structured content gets a stage of the page compiler that reads it from Markdown, as `FileTree` has, because agents write Markdown reliably and the compiler can check it. A component that declares itself wide may use the breakout track; see [page layout](web-app#page-layout).

## Design decisions

An element has a role or a category, and its color comes from the theme. A color written in the page would break in the light theme, in print, and with forced colors.

A step changes only emphasis and visibility, because elements that moved between steps would make the user lose track of them.

Tab sets are linked by their labels, so a tab set needs no group key. Unrelated sets with the same labels then change together, which is one reason content to compare goes in columns.
