# Components

This page lists everything a page or a chat reply can contain and shows an example of each item. For each item, it says where its code is, whether it is numbered, what the reader can link to or ask about, and what the compiler checks. How authors write each component is in the authoring reference, [`starter/docs/components.md`](/-/files/yapparatus/starter/docs/components.md).

1. **Every component also works in chat replies,** without imports and with the same line length as the page. In a reply, nothing is numbered and there are no Link or Ask buttons, because a reply is not part of the document.
2. **A failed check is reported by its code.** Each code in the Checks column is an error in the registry, except some diagram and chart codes, which are warnings. The server reports each problem with its file and line, and it refuses a reply that contains one. See [diagnostics](diagnostics#codes-and-severity).
3. **A selection gives more precise context than the buttons.** A selection in a list item or a table row points at that line. See [capturing a selection](addresses-and-context#capturing-a-selection).

## Text and Markdown

Headings, paragraphs, lists, links, emphasis, inline code, images, quotations, rules, and tables are ordinary Markdown. [`src/reader/prose.tsx`](/-/files/yapparatus/src/reader/prose.tsx) gives each one its style.

- **Headings** use `##` and `###` only. Both levels are numbered and listed in the contents. A deeper level would be neither numbered nor listed.
- **Links** are checked. A link to a page or anchor that does not exist is an error.
- **Tables** align text to the left and numbers to the right. Numbers use tabular figures, which all have the same width. Each header is aligned like its column. With this alignment, the reader can easily compare values down a column. Long cells keep a readable width. Wrap a table in `Table` to give it a number and a caption.

> A quotation without a marker stays a quotation, like this one.

## Alerts

> [!NOTE]
> A note adds something the reader may want to know.

> [!WARNING]
> A warning is for a step that can lose data or break something.

An alert is a blockquote whose first line is `[!NOTE]`, `[!TIP]`, `[!IMPORTANT]`, `[!WARNING]`, or `[!CAUTION]`. The compiler removes the marker and passes the kind to the reader, which draws the icon, the title, and the color. Other markers are an error. The syntax is the same as on GitHub, so agents already know it, and replies need no extra component. An alert is one or two sentences.

## Code

A fenced code block is highlighted at build time with the theme colors, and it never wraps. The block names a language that Shiki, the highlighter, knows, or `text`. The reader therefore always sees highlighted code. Common languages are loaded when the server starts. Any other language is loaded when a page first uses it.

Code marks show what changed in a block:

```ts
const retry = {
  attempts: 3, // [!code --]
  attempts: 5, // [!code ++]
  delayMs: 200, // [!code highlight]
};
```

The marks are comments at the end of a line, and the compiler removes them before highlighting. They show what changed without a second copy of the code. The Copy button copies the code after the change.

**Line length is a recommendation and is not checked.** Code written for a document stays within 100 columns, so it fits the breakout track without scrolling. Code copied from a source keeps its formatting, because the reader may compare it with the original.

`Excerpt` shows lines of an external file in the same kind of block, with the file's line numbers and a link to the file. See [external files](rendering#external-files). `Listing` gives a block a number and a caption, as in <Ref to="listing-example" />. This listing shows the current content of this repository's [registry](/-/files/yapparatus/src/reader/registry.ts).

## Figures, diagrams, and charts

`Figure` puts a frame around any content, usually an image, and adds a number and a caption below it. A figure is at least as wide as the text. The content is centered, and the caption has the same line length as the text. <Ref to="figure-example" /> frames three icons.

<Figure id="figure-example" caption="A figure that frames icons." description="Three icons in a row: a database, a gateway, and a battery">
  <Icon name="lucide:database" size={32} label="Database" /> <Icon name="local:gateway" size={32} label="Gateway" /> <Icon name="energy-icons:battery-bolt-20" size={32} label="Battery" />
</Figure>

`Diagram` draws a figure from a short program and numbers it like a `Figure`. Every part has an address that the reader can link to and ask about, and `Step` children explain the figure in order. <Ref to="diagram-example" /> has two steps. [Diagrams](diagrams) describes the compiler.

  d.arrow(reader, page, "reads")

  <Step focus="reader">The reader opens the document.</Step>

`Chart` draws data with Observable Plot and numbers it like a `Figure`. Its data is a `Table` on the page, a block of CSV inside it, or a file. <Ref to="chart-example" /> draws a few rows written in the page. [Charts](charts) describes how it works.

## References and icons

`Ref` links to a numbered item or a section and shows its current number. For example, <Ref to="alerts" /> describes alerts. A `Ref` to an id that does not exist is an error.

`Icon` shows an icon from an installed collection or from `icons/`, such as <Icon name="lucide:folder" label="Folder" />. The name is a literal string, and the compiler turns it into an import of that one icon. An unknown name stops the page from compiling.

## Tabs and columns

`Tabs` and `Columns` hold the same thing, labelled `Panel`s, and differ in what the reader does with them. Tabs show one panel at a time, and the reader picks the one that applies, such as the form a document is read in. Columns show every panel side by side, and the reader compares them, such as an old and a new design. <Ref to="file-tree-source" /> puts a source beside its result.

<Tabs>
<Panel label="Live">

```sh
pnpm dev                # the reader and the chat, on a local server
```

</Panel>
<Panel label="Website">

```sh
pnpm build              # dist/: a static site
```

</Panel>
<Panel label="Single file">

```sh
pnpm build:single       # dist-single/index.html: one offline file
```

</Panel>
</Tabs>

1. **One panel, two ways to show it.** A reader cannot compare what is hidden, so content to compare is never in tabs. Both containers take the same panels, and an author changes one into the other by renaming the outer tag.
2. **A choice follows its label.** Choosing a tab selects the tab with the same label in every set, on every page, and the browser keeps the choice for the next visit. Sets are matched by their labels, with no group key, so an author has nothing to choose or forget. Unrelated sets with the same labels also follow each other, which is one more reason that a before and an after belong in columns.
3. **Hidden panels can be found and printed.** A hidden panel is `hidden="until-found"`. Find in page reveals it and selects its tab in that set only, without changing the reader's choice. Print shows every panel under its label. The tabs follow the WAI-ARIA tabs pattern: the arrow keys, Home, and End move between tabs.
4. **Columns are numbered by what they hold.** Columns alone hold text and are not numbered. Code side by side goes in a `Listing` and drawings side by side in a `Figure`, and the container then takes the full width. A diagram or chart inside a figure is part of it: it draws no frame and has no `id` or `caption` of its own, which the compiler reports as `FIGURE_NESTED`.
5. **Columns line up.** The last block of each column fills the column's height, so code blocks side by side end on one line. Up to three columns fit, and on a narrow page they stack.
6. **The compiler reads the panels.** It passes their labels to the container, so the reader never inspects its children. It reports content outside a panel and fewer than two panels as `PANEL_CONTENT`, a missing or repeated label as `PANEL_LABEL`, a panel outside a container and a container inside a panel as `PANEL_NESTED`, and more than three columns as `TOO_MANY_COLUMNS`.

## Custom components

A document can import its own React components from `.tsx` files. These components work in that document's pages and use the exported theme. The color samples in [styling](styling#color) are a custom component of this document. Custom components are not available in chat replies, because a reply has no imports. See [styling](styling).

## Adding a component

A new built-in component is added in these places, in one change:

1. [`src/reader/registry.ts`](/-/files/yapparatus/src/reader/registry.ts), so pages and replies can use it without an import.
2. `pageComponents` in [`src/document.ts`](/-/files/yapparatus/src/document.ts), so the reply check accepts it.
3. The component list in [`src/server/prompt.ts`](/-/files/yapparatus/src/server/prompt.ts), which the agent reads.
4. The authoring guide and [`starter/docs/components.md`](/-/files/yapparatus/starter/docs/components.md).
5. This page: a row in <Ref to="component-inventory" /> and an example.

**Structured content is written as Markdown.** For a component such as `FileTree`, the author writes Markdown, and the compiler turns it into props. Agents write Markdown reliably, and the compiler can check it.
