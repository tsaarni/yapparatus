# Server

The server is the dev server: Vite with the `yapparatus()` plugin, serving one document. The plugin combines the [page compiler](page-compiler)'s plugins with the server, which it installs when Vite starts the dev server. This page describes what the server stores and computes. The requests and their bodies are in [the REST API](rest-api).

## Starting

The `yap` command takes a subcommand and a document directory, as in `yap dev docs/design`. The other subcommands are `preview` and [`build`](page-compiler#builds).

The current directory is the project and Vite's root, and a project's `vite.config.ts` can add Vite options and plugins. The plugin stops with an error when the document directory is outside the project, has no `document.json`, or lies inside or around another document directory.

The server listens on `127.0.0.1` only. When it starts, it writes its address to `.yapparatus/server.json` in the project, as `{"url":"http://127.0.0.1:5173"}`. The agent library reads this file to find the server. A closing server removes the file only if it still holds that server's address.

## Chat log

The chat of a document is a log in `.yapparatus/<directory>/chat.jsonl`, with one JSON object per line. `<directory>` is the path of the document directory. The chat log module keeps the log in memory and appends each new message as one line. It never rewrites a line. <Ref to="server-chat-record" /> shows a reader message and the reply to it.

`seq` is the message's place in the log, starting at 1. A reply names in `inReplyTo` the newest reader message it answers, and the earlier unanswered reader messages count as answered too. `repliedTo` is the highest `inReplyTo` in the log. The reader messages after it are unanswered.

`createdAt` is when the server stored the message. `readAt` on a reply is when the server first gave the answered message to an agent. The server keeps that time in memory only, so a reply after a restart has no `readAt`.

A reader message holds its text and its [references](documents#references). A reply holds the path of its MDX file, `.yapparatus/<directory>/chat/<uuid>.mdx`, which the web app imports to show it. The name is random, so a new reply never reuses the address of a deleted one. Clearing the chat deletes the reply files and empties `chat.jsonl`, and numbering starts again at 1.

The server computes the state when it is asked, in this order:

1. If a read of the current agent is open, or its last empty read or reply ended less than 10 s ago, the state is `waiting`.
2. Otherwise, if the agent was given a reader message less than 10 minutes ago and no reply has answered it, the state is `working`.
3. Otherwise the state is `away`.

A timer runs out with each time limit, so the web app learns that the agent went away without a new request. <Ref to="server-agent-labels" /> lists the labels that the [chat panel](web-app#chat-panel) shows.

<Table id="server-agent-labels" caption="The agent states and their labels in the web app.">

| State | Meaning | Label in the web app |
|---|---|---|
| `waiting` | A read is open, or one ended a moment ago | Agent connected |
| `working` | The agent read messages it has not replied to | Agent working, not connected |
| `away` | Neither | Agent not connected |

</Table>

`working` is an estimate, and the 10 minute limit bounds how long a wrong estimate is shown.

## What the agent has to do

A read of the chat with the `Yapparatus-Agent` header is an agent's read. It returns what the agent has to do instead of the whole chat: every reader message after `repliedTo`, the new errors when the read asks for diagnostics, and a [prompt](agent-library#prompts) for both that ends with the command to run next. An error is new when it has lasted 2 s and the agent has not been given it, as [diagnostics](diagnostics#what-the-agent-sees) describes.

The server remembers in memory what the reads returned. The newest reader message is the one that the next reply answers, and the errors count as given, so a later read does not return them. Messages that the agent read and did not answer come back on the next read.

Each agent read carries a random agent id in the header, and the newest id becomes the current agent. The reads of earlier ids end with `409`, so a wait command left running by an old agent session cannot take messages meant for a new one.

A read with `wait` stays open while it would return nothing. When the chat or the diagnostics change, the server computes each open read again and answers those that now have something.

## Reply checks

A reply is an agent's `POST` with MDX. The server refuses it with `409` when no agent read has returned a reader message since the chat was last cleared. Otherwise it checks the reply and stores it:

1. An empty reply is refused with `REPLY_EMPTY`.
2. The MDX is written to a temporary file in the chat directory and compiled through Vite with the [page compiler](page-compiler#replies). A failure is `COMPILE_FAILED`.
3. The server collects the errors: every error the page compiler found, components that are not built in (`UNKNOWN_COMPONENT`), and links that do not resolve. Warnings do not refuse a reply.
4. With errors, the server deletes the temporary file and answers `422` with the errors. Without errors, it renames the file to a random name and appends the message to the log.

Errors in the pages do not hold back a reply. Reader messages sent while the agent wrote the reply stay unanswered.

## Diagnostic store

The diagnostic store holds the diagnostics of the document and answers the requests of the `diagnostics` resource. After each file change, it compiles every page and checks the links and `document.json`. It also keeps what browsers report for each page and each reply. How diagnostics are found, when an error becomes new for the agent, and how a read waits for recent checks are described in [diagnostics](diagnostics).

## External files

The file handler answers reads of external files for the [file view](web-app#file-view). The server reads a file only from a directory that `"files"` in `document.json` names, and only when the file's real path stays inside that directory. It refuses files under `.git`, files over 1 MB, and files that contain a NUL byte. The server watches each file it has served. When the file changes, the server sends its address as an update, and an open file view reads it again.

## Pictures

The picture handler draws a diagram as a PNG for the agent, without a browser. If the page file changed since its last compile, the handler compiles it first, so the picture matches the file on disk. [The diagram compiler](diagram-compiler#pictures) describes how it draws.

## Updates

The server sends changes to the web app on Vite's hot-update connection. It collects changes for 50 ms and then sends the latest data of each event, so a burst of edits produces one update. The chat and the diagnostics are one event each, and each changed external file is its own event. The server ignores changes to files under `.yapparatus/`, so storing a reply does not count as a change to the document. The events and their data are listed in [the REST API](rest-api#updates).

## Security

The server trusts local processes, which can already read and write the project, and uses no token. It guards against web pages in the user's browser and DNS rebinding. It listens on `127.0.0.1`, so other machines cannot reach it. The router answers `403` to a request whose `Origin` header is not `http://` followed by the request's `Host`. The web app sends its own origin, and the agent library sends no `Origin` header. Vite checks the `Host` header against its allowed hosts before the router sees the request, which blocks DNS rebinding.

## Logging

The server, the web app, and the agent library share one logger. The environment variable `YAPPARATUS_LOG` sets the level everywhere: `debug`, `info`, `warn` (the default), `error`, or `silent`. The server passes its level to the web app. In Node every line goes to stderr, because the agent reads the agent library's stdout as its prompt.
