# Agent library

The agent library is the package export `yapparatus/agent`. The agent calls it from shell commands to wait for the user's messages, reply, check the document, and look at diagrams. This page describes the calls, the commands that run them, and the prompts the agent reads.

## Overview

The agent runs in its own terminal, and the server does not start it. The agent runs a loop of commands, and the server answers each request. <Ref to="agent-round" /> shows one round, from a wait to the next wait.

## Commands

A command runs TypeScript with Node from the project directory, with the code in the `-e` argument so that stdin stays free for the reply. <Ref to="agent-reply-command" /> shows the command that replies and then waits, as the server prints it.

<Listing id="agent-reply-command" caption="The command that sends a reply and waits for the next message.">

```sh
node --input-type=module-typescript -e 'import { sendReply, waitForMessage } from "yapparatus/agent"; await sendReply(); console.log((await waitForMessage()).prompt);' <<'MDX'
<your reply>
MDX
```

</Listing>

The server writes every command, and each prompt ends with the command to run next. The code uses only double quotes, because a single quote would end the shell argument. The reply goes in a quoted heredoc, `<<'MDX'`, so the shell expands nothing in it, or comes from a file with `< reply.mdx`. When `sendReply()` rejects, `waitForMessage()` does not run, and the output is the error.

## waitForMessage

`waitForMessage()` resolves with the unanswered reader messages and the errors that the agent has not been given. It takes no arguments, because [the server remembers both](server#what-the-agent-has-to-do).

Each call makes a random agent id and sends it in the `Yapparatus-Agent` header of every read. The call reads with `wait=25` and repeats the read until the answer holds a message or an error. The start prompt tells the agent to run the wait command in the background when its shell notifies it of finished commands, and otherwise with the longest shell timeout, running it again when the shell stops it.

A call that is killed before it prints loses nothing, because the next call returns the same unanswered messages.

## sendReply

`sendReply()` reads the reply's MDX from stdin and sends it as `{ "author": "agent", "mdx": … }`. It answers the reader messages that the last wait returned. When stdin is a terminal, it rejects at once instead of waiting for input.

The server [checks the reply](server#reply-checks) before it stores it. A refused reply rejects with a `YapparatusError` whose message lists the errors and what to do next, and whose `diagnostics` hold the errors as data.

## checkDocument

`checkDocument()` resolves with every diagnostic once the checks of recent edits are done, the pages that no browser has checked since they changed, and a prompt that lists both. The agent runs it after editing and before replying. It sends no agent id, so it can run while a wait is open. What the list holds is described in [diagnostics](diagnostics#what-the-agent-sees).

## savePicture

`savePicture(address, file, options?)` saves a diagram's picture as a PNG in the file that the agent names. The address is the figure's `/page#figure`. With `{ ids: true }`, the picture labels each element with its id and outlines the elements that diagnostics name. The agent opens the file as an image and deletes it afterwards. The picture shows what no diagnostic covers, such as a layout that is valid but hard to read, so the start prompt asks the agent to look once after it changes a diagram and the check is clean.

## Prompts

A prompt is text the server writes for the agent. The library passes it on unchanged and writes only its own connection errors. <Ref to="agent-prompts" /> lists the prompts.

<Table id="agent-prompts" caption="The prompts the server writes, and when the agent reads each.">

| Prompt | When | Ends with |
|---|---|---|
| Start prompt | The user pastes it into a new agent session. It is the `prompt` of a whole read of the chat | The wait command, then the check and picture commands |
| Messages | A wait returns reader messages | The check command, then the reply command |
| Errors | A wait returns new errors and no message | The check command, then the reply command, or the wait command when no message was given yet |
| Idle | An agent's read returns nothing. `waitForMessage()` reads again instead of returning it | The wait command |
| Diagnostics | `checkDocument()` returns | The list alone |
| Refused reply | The server refuses a reply | "Fix the MDX and run the command again." |
| Nothing to answer | A reply has no message to answer | The wait command |
| Taken over | Another agent took over | "Stop waiting." |

</Table>

The start prompt holds the instructions for the whole session: where the authoring guide is, which components a reply may use, how to run the wait command, and when to check the document and look at a picture. It also lists the external directories, so the agent can open the files that references name. Later prompts hold only the messages, the diagnostics, and the next commands. The commands take no arguments, so the loop keeps working after the agent compacts its conversation.

The prompt calls the user the reader, so that the agent can tell comments from the chat from what the user types directly to the agent. Each message is a `<reader_message>` element that holds only the reader's text, so the agent can tell it from the server's instructions. A closing tag in the text is escaped, so the text cannot end the element. The element carries the time the message was written, because the web app shows no message numbers.

Each reference is one line: its kind, its file and the lines the user saw, its address, and the selected words or the open diagram step. The prompt points at the lines instead of copying them, because the agent can open the file. The references follow the element, because the server writes them. One sentence after all the messages tells the agent to find a reference by its address and words when its file changed.

The diagnostics part has the format that [diagnostics](diagnostics#what-the-agent-sees) describes, with the new errors first.

## Errors and retries

Every failure rejects the call with a `YapparatusError`. Its message is the server's `error`, or the library's own text when the server cannot be reached.

`waitForMessage()` repeats reads of 25 s instead of sending one long request, because Node's `fetch` gives up after 300 s without response headers, and a restart of the server drops a waiting request. Each request is aborted after 35 s, 10 s longer than the server holds it.

When the server does not answer, `waitForMessage()` tries again every second for 30 s, so a restarting server does not end the wait. After 30 s it rejects with instructions to start the server. The other calls do not retry.

When [a newer agent](server#what-the-agent-has-to-do) reads the chat, the older agent's `waitForMessage()` rejects with "Another agent took over the chat. Stop waiting."

A `YapparatusError` that a command does not catch is printed to stderr without a stack trace, and the process exits with code 1. Other errors keep their stack. The agent needs the instructions for the fix, and a stack trace does not help it.

## Packaging

Commands import the library as `yapparatus/agent`. The export points at compiled JavaScript and type declarations. A project that installs the package compiles them in the package's `prepare` script. The library cannot ship as TypeScript, because Node does not strip types from files inside `node_modules`.

Commands use erasable TypeScript only: TypeScript whose types can be removed without changing the code. Node removes the types without checking them, and an enum or a parameter property is an error.

Each call finds the server through `.yapparatus/server.json` in the current directory or the nearest one above it, so a command names no document and no port. Without the file, or when the file is stale after a crash, the call rejects with instructions to start the server. The library [logs](server#logging) to stderr.

## Design decisions

### Commands that call a library

Commands that call a library work with the agent the user already uses, often the session that wrote the document. <Ref to="agent-alternatives" /> lists the alternatives that were considered.

<Table id="agent-alternatives" caption="Ways to connect the agent that were considered, and why each was not chosen.">

| Alternative | Why not |
|---|---|
| ACP (Agent Client Protocol) | Works with few agents. It starts a fresh session that does not know how the document was written, and leaves permissions and reconnection to the server |
| MCP (Model Context Protocol) | Cannot tell an agent that the user wrote a message. It needs configuration for each agent, and the client sets the timeouts of tool calls. Every coding agent can run Node |
| A CLI | Returns only text. A library returns data that the agent can filter and combine, and one command can both reply and wait |
| Copy and paste | A person moves every message between the web app and the agent by hand |

</Table>

### Text written by the server

The server writes the prompts, the commands, and the error texts, next to the requests they describe, so all the wording the agent reads is in one place.

### The reply on stdin

A reply could be an argument of `sendReply()`, written as a string in the command. MDX has many backticks and quotes, and in a JavaScript template literal `${` becomes code. Stdin with a quoted heredoc needs no escaping.

### No request ids

`sendReply()` does not retry, and requests carry no ids, so an agent that runs the reply command again after a lost response stores the reply twice. On localhost a lost response is rare, and a duplicate reply is harmless.

### Open questions

- Whether every supported agent can run commands in the background and be notified when they finish, or whether some agents must restart the wait after their shell stops it.
- Whether agents keep the wait loop running over a long session, or end their turn and stop waiting.
