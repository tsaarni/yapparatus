# Rendering pages

This page describes how a page file is compiled and then rendered on screen, how the page is laid out and numbered, how it shows external files, and how a document is built for other readers. The rules behind type and color are in [styling](styling).

## Pages

1. **A page's file name is its address.** `key-ideas.mdx` is served at `/key-ideas`, and subdirectories become path segments. Names use lowercase letters, digits, and hyphens. The file name, the page id, and the address are the same name, so no code converts between them.
2. **`document.json` lists every page file once, in reading order.** The list contains file names, such as `overview.mdx`, so it matches the files on disk. The address is the file name without the extension. The compiler reports an error for a page file that is not in the list and for a listed page that has no file. The order is in one place. Numbers in file names or in frontmatter would put the order in every file.
3. **A page has one `#` heading, which is the title.** A separate title field would repeat the heading, and the two could differ.

<Ref to="page-pipeline" /> follows one file through these steps. Steps 1 to 5 are the page compiler, which runs in the dev server or in a build. It records what the page contains and reports the problems it finds as [diagnostics](diagnostics).

1. **Page list.** The plugin checks the page names and the list in `document.json`. It then generates the module `virtual:yapparatus/document`, which lists the pages in the order of `document.json`. The module holds each page's outline (step 5) and a function that loads the page's code. When a file is added or the list is edited, the module updates without a restart.
2. **MDX parser.** The parser reads Markdown with GitHub-flavored tables, component tags, and JavaScript in braces. A diagram's `draw` is therefore an ordinary function, which the diagram step runs. Headings get GitHub-style anchors. The conventions step then turns alerts and file trees into components, marks code lines, and checks code languages and heading depth. See [components](components).
3. **Icon step.** An `<Icon name="…">` with a literal name becomes an import of that one SVG file, so a page includes only the icons it uses. The compiler cannot resolve a name that is built at run time, so it reports an error.
4. **Diagram step.** Each `<Diagram>`'s `draw` runs in the server process, and the figure is compiled with the reader's font files and checked with its steps. The drawing replaces `draw` in the page as data, and its problems are the page's diagnostics. The page that reaches the browser has no draw program and needs no compiler. See [where a diagram is compiled](diagrams#where-a-diagram-is-compiled).
5. **Outline and source marks.** The outline records the title, sections, numbered blocks, ids, links, and references. Numbering and link checking use the outline. The outline step marks each top-level block, list item, and table row with its file, its lines, and a hash of its source lines. It marks each line of a code block with its line in the page. With these marks, the reader app maps a selection to its source lines, so authors do not give paragraphs ids. The page shows no line numbers, because line numbers of the page file are not useful to a reader. See [asking about the page](reader-app#asking-about-the-page).

## Rendering a page

Steps 6 and 7 render the page in the browser.

6. **Reader app.** The router picks the page from the address, loads the page's code, and renders it with styled Markdown elements and the page components. Pages use the components without imports. A diagram draws the drawing that the page compiler made.
7. **The screen.** StyleX compiles the styles at build time. See [styling](styling).

**The browser draws charts when it renders the page.** A chart's `plot` runs in the browser at the width of the page, so the page compiler checks only its data; see [external files](#external-files). The browser reports a chart's diagnostics when a reader opens the page. See [diagnostics](diagnostics).


**A page's code loads when the page is first shown.** The page list holds every outline, so the contents, the numbers, `Ref`, and the file view's list of sections need no page's code. Only the page on screen runs its code. A document with many diagrams and code blocks therefore starts as fast as a small one.

1. **The page list keeps every outline.** In the dev server, the plugin compiles each page for its outline, in the same environment as the server's checks. A build loads each page module, which it bundles anyway. A page that does not compile gets an empty outline titled with its id. The reader lists the page, and opening it shows its error.
2. **The router switches to a page when its code has loaded.** The address changes at once, and the old page stays on screen until the new page's code has loaded, so the reader never sees an empty page. When the reader follows another link or goes back in the meantime, the latest address wins. The app renders for the first time when the page at the address has loaded.
3. **A page arrives with its content.** Scrolling to an anchor, returning to the position on Back, Show on page, and Ask on a diagnostic therefore find the page's content in the document. A page whose code fails to load is shown with its error.
4. **The reader app loads a page before it is needed.** It starts loading the page a link goes to when the pointer or the focus reaches the link, and the next page when the browser is idle.

**The browser replaces an edited page without a reload.** The page list accepts the update and replaces the page's module and outline. The numbers, the contents, and the links then update to match. The dev server also marks the page list as changed, so a reload compiles it with the new outline. A reload would make the page flash, and the reader would lose their place while an agent edits. Pages do not use React Fast Refresh. They export `outline`, and Fast Refresh answers that export with a full reload. The chat is rendered outside the page component, so an update keeps the reader's draft and selections.

## Layout

The page uses a grid with a text column for prose and a breakout track beside it for wide content, as <Ref to="breakout-grid" /> shows.

<Diagram id="breakout-grid" caption="The breakout grid. Text uses the text column, and a large figure also uses the breakout track." draw={(d) => {
  const text = d.box("text column", { id: "text-column", sub: "560 px for reading", width: 300, height: 96 })
  const track = d.box("breakout track", { id: "breakout-track", sub: "460 px", width: 220, height: 96, role: "muted" })
  const columns = d.row([text, track], { gap: 12 })
  const narrow = d.box("small figure", { id: "small-figure", sub: "at least the text width", width: 300 })
  const wide = d.box("large figure", { id: "large-figure", sub: "grows into the track", width: 532, role: "accent" })
  d.place(narrow, { below: columns, gap: 20, align: "start" })
  d.place(wide, { below: narrow, gap: 16, align: "start" })
}} />

1. **Prose lines hold 45 to 75 characters.** The text column is 560 px wide, which is about 73 characters. Longer lines make it harder to find the start of the next line. WCAG AAA sets the limit at 80 characters.
2. **All content starts at one left edge.** The title, text, lists, code, tables, and figures start at the same horizontal position. This gives the page a clear structure.
3. **Figures, tables, and code may break out.** They grow to the right into the 460 px breakout track, but only as far as their content needs. The width of an element therefore depends only on its content.
4. **The breakout track shrinks first.** When space is short, the breakout track shrinks, and then the text column shrinks.
5. **Wide content scrolls.** Drawings shrink down to 75 % of their size and then scroll sideways, because labels in a smaller drawing are too small to read. Code lines do not wrap by default, because wrapping would show line breaks that are not in the source. Tables scroll when they are wider than the page.
6. **The layout is centered and at most 1440 px wide,** so content does not stretch on very wide screens.
7. **Reading styles respond to the width of the reading column.** When the column is narrower than 600 px, the title, the lead paragraph, and the figure padding become smaller. The column is narrower on a phone and when the chat grows. Measuring the column covers both cases. See [styling](styling#tokens).

## Numbering and references

Numbering follows the Chicago Manual of Style and common technical-writing guides.

1. **Chapters, sections, and titled figures, tables, and code listings are numbered.** Asides, inline snippets, and untitled examples are not.
2. **Each kind has its own sequence per chapter,** so Figure 3.1 and Table 3.1 can both exist.
3. **Every numbered item has a title and an `id`, and is referenced in the text.** A number that no text refers to has no use.
4. **Tables and listings have their titles above, figures below,** as in print.
5. **Numbers are generated.** They change as the document grows, so authors do not type them. `<Ref>` shows the current number, and a broken `Ref` is an error.
6. **A document can turn numbering off,** for all kinds with `"numbering": false` in `document.json` or per kind with `{ "sections": false }`, using the keys `sections`, `figures`, `tables`, and `listings`. Ids, addresses, and `Ref` work the same, and a `Ref` then shows the caption, heading, or page title.

## External files

A document includes files from outside its project, such as the code it explains, through external directories. Pages can show any text file from these directories, including files that are not code. `document.json` lists each directory under `"files"`, with a path relative to `document.json`. Pages refer to files in these directories with file addresses. See [addresses](addresses-and-context#addresses). <Ref to="code-flow" /> shows how code goes from a directory to the reader, and how a question about the code reaches the agent.

  d.equalSize([directory, page, view, item, agent])

  d.place(item, { below: view, gap: 88 })

1. **An excerpt is read when the page is compiled.** `<Excerpt from="/-/files/app/main.go" start="func (s *Server) Handle(" />` becomes a code block in the file's language. The page depends on the file, so an edit to the file updates the page. A build contains the excerpted lines, so it does not need the directory.
2. **Excerpts find their lines by text.** Line numbers change whenever lines are added above them, and an excerpt with line numbers could show the wrong code without an error. `start` quotes text from the first line of the excerpt. Exactly one line in the file may contain this text. The excerpt continues to the end of the block that this line opens, or to the line that `end` quotes. When the file no longer contains the quoted text, the compiler reports an error at the page's line, like a broken link. This design follows the `start-after` option of [Sphinx](https://www.sphinx-doc.org/en/master/usage/restructuredtext/directives.html#directive-literalinclude). The marker comments of [mdBook](https://rust-lang.github.io/mdBook/format/mdbook.html#including-portions-of-a-file) would change the external file. A document often shows a repository that its author does not own, so Yapparatus leaves the file unchanged.
3. **Excerpts keep the file's text and line numbers.** Code marks written in the file are shown as ordinary text. The `mark` prop highlights the lines that contain its text. Line numbers are drawn outside the code's text, so copying or selecting takes only the code. Links into a file use line numbers. A link opens the whole file and scrolls to the lines. Long lines scroll, so the code keeps its layout. The author adds `wrap` when the words of a long line matter more than its layout, such as a sentence or table row of a Markdown file. A wrapped line keeps one number, and its continuation rows start where its text starts.
4. **The page compiler checks a chart's data,** like an excerpt. The data is a block inside the chart, or the table or file that the chart names. The rows of a file are loaded in a separate module. See [charts](charts#where-the-data-comes-from).
5. **The file view shows a whole file at the file's address.** It uses the same code block as an excerpt. It also lists the sections that link to the file or excerpt from it. The reader can go from the code to the text and from the text to the code. `#L11-L14` highlights those lines and scrolls to them.
6. **Files are read only from the directories named in `document.json`.** The server refuses paths that leave the directory, including paths through symbolic links. It also refuses files inside `.git`, files over 1 MB, and binary files. This stops a document from exposing other files on the disk.
7. **An external directory can be anywhere on disk.** A path under `"files"` may point outside the project, such as `"../../contour"`, so one document can show several repositories. The pages, `document.json`, and `.yapparatus/` stay in the project where the server runs. The agent runs its snippets in the project directory, because the library finds the server through `.yapparatus/server.json`. Prompts name files relative to the project directory. The agent therefore opens `../../contour/internal/dag/builder.go` exactly as written, if it has permission to read outside its directory.
8. **Each file is named twice, and the two names must agree.** The address names the directory by its name in `document.json`. The path names the file on disk. Two directories can contain the same path, such as `src/main.ts`, and the directory names tell them apart. The server refuses a context item whose path is not the file that its address names.

## Building for sharing

<Diagram id="three-outputs" caption="The same reader app, in three forms. Only live mode has the chat." draw={(d) => {
  const source = d.box("Document directory", { id: "document-directory", sub: "pages and document.json" })
  const live = d.box("pnpm dev <directory>", { id: "out-live", mono: true, sub: "live, with chat", role: "accent" })
  const site = d.box("pnpm build <directory>", { id: "out-site", mono: true, sub: "dist/<directory>/ website" })
  const single = d.box("pnpm build:single <directory>", { id: "out-single", mono: true, sub: "one HTML file" })
  d.equalSize([live, site, single])
  const outs = d.row([live, site, single], { gap: 32 })
  d.place(source, { above: outs, gap: 64 })
  for (const out of [live, site, single])
    d.arrow(source.bottom, out.top, { route: { viaY: d.lerp(source.bottom, out.top) } })
}} />

1. **The same app is built in three forms,** as <Ref to="three-outputs" /> shows. All three use the same reader app, styles, and page compiler. In each form, the page compiler compiles the diagrams, and the browser draws the same drawings.
2. **Builds have no chat** and make no requests to a backend. A shared document is read-only.
3. **A build contains no chat state.** A build includes only the pages of the document directory and leaves out `.yapparatus/`. Sharing a document therefore does not share the conversation about it.
4. **Every address is a file in the website build,** and the build also contains `404.html`. Any static host can therefore serve links to any page and section.
5. **Each page is its own file of code in the website build.** A page's HTML file preloads that code with the app, and the root preloads the first page, so the first page shows without a second request.
6. **The single file uses `#/page#anchor` addresses** and embeds all pages, fonts, and assets. The file needs no server and works offline when opened from disk. Each page's code is in the file, and it runs when the page is first shown.
7. **A build contains the external files that its pages name, and no other files.** For every file address in a page that names a readable file, the build contains the highlighted file, as the same JSON that the server returns in live mode. The build wraps it in `JSON.parse` of a string, which the browser parses faster than an object written as code. In the website build, each such address is its own file. An author publishes a file by naming it in a page. A build does not copy whole directories.
